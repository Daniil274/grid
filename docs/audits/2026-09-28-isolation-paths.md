## 2. Где лежит рабочая папка на хосте

### Было

| Режим | Рабочая папка |
|---|---|
| Веб-чат / `agent_chat`, изоляция выключена | рабочая директория конфига или `--path` |
| Веб-чат / `agent_chat`, изоляция включена | `--path`, иначе `<папка конфига>/workspace/user_<user_id>` (`user_id` из `--user-id`, по умолчанию `default_user`) |
| `ContainerManager` без явной папки | `<рабочая директория конфига>/user_<user_id>` |

Разговоры (`logs/context.json`) и SDK-сессии (`logs/agent_sessions.db`) лежали в `logs/` системы — одни на всех.

### Стало

**Однопользовательский сервер** — так же, как было: `--path`, иначе папка из конфига; при включённом флаге изоляции — `<папка конфига>/workspace/user_<id>`, чтобы контейнер не смонтировал саму папку конфига.

**Сервер с аккаунтами** (`--data-dir`, по умолчанию `~/.grid/web`):

```
~/.grid/web/
├── accounts.db                 аккаунты, сессии, приглашения, учёт ходов
└── users/<id>/                 id — 32 hex-символа, безопасен как имя папки
    ├── workspace/              ← единственное, что видит контейнер
    ├── conversations.json      разговоры
    ├── agent_sessions.db       SDK-сессии агентов
    ├── agents.json             личные агенты
    └── logs/                   логи ходов этого пользователя
```

Служебные записи лежат **рядом** с `workspace/`, а не внутри: из контейнера и файловыми инструментами до них не добраться.

Запасной путь `ContainerManager` (`<рабочая директория>/user_<id>`) удалён вместе с неиспользуемыми `get_container_id` и `exec_command`. Путь монтирования теперь всегда передаёт вызывающий код. Он приводится к одному написанию (`resolve()`) и для монтирования, и для проверки существующего контейнера. Раньше проверка сравнивала `resolve()`, а создание брало `absolute()`: при ссылке в пути контейнер пересоздавался бы при каждом обращении.

## 4. Как агент видит пути

Не менялось (`utils/path_utils.py`):

- с контейнером корень агента `/` — это рабочая папка; абсолютный путь агента читается от этого корня;
- «утёкший» абсолютный путь хоста принимается, только если он внутри рабочей папки;
- выход за рабочую папку (`..`, ссылки после `resolve()`) — отказ;
- в тексте для агента путь хоста заменяется на `./`.

Добавлено в интерфейсе: реальный путь рабочей папки и пути конфигов систем видят только администраторы; остальным показывается «your workspace».

## 5. Где выполняется каждый инструмент

| Инструмент | Было | Стало |
|---|---|---|
| `bash_tool` | на хосте, `cwd` = папка пользователя на хосте | `docker exec -w /workspace/<подпапка> … timeout -k 5 N sh -c`; на хосте — только без контейнера |
| git (`git_log`), beads | `docker exec`, путь переводится в `/workspace/…` | так же, помечены `CONTAINER` |
| MCP-серверы (`codegraph` и др.) | `docker exec -i -w /workspace` | так же, в `McpServers`; сервер привязан к инструменту, папке и контейнеру и не достаётся чужой папке |
| `file_read/write/append/edit`, блокнот | процесс сервера на хосте, проверка пути | то же, плюс на Linux-хосте обход пути от корня папки через `dir_fd` + `O_NOFOLLOW` (`utils/confined_fs.py`): контейнер не подменит папку на ссылку на `/` между проверкой и открытием |
| поиск (`rg`) | процесс сервера, проверка пути | то же, плюс `--no-config --regexp … --`: запрос агента не станет флагом `rg` |
| web-инструменты | процесс сервера | то же, плюс защита от SSRF: только публичные адреса, редиректы проверяются вручную |
| инструменты без пометки `TOOL_ISOLATION` | выдавались | с аккаунтами не выдаются (в лог пишется предупреждение) |

## 6. Образ песочницы

**Было.** `grid-agent:latest` собран 20.09 из Dockerfile, который 22.09 (`8dac8b9`) превратили в образ сервера. Рецепта песочницы в репозитории не осталось. Пересборка корневым Dockerfile дала бы образ без пользователя `agent` и с веб-сервером в каждом контейнере. В старом образе нет `codegraph`, поэтому MCP-сервер `codegraph` в контейнере не запускался.

**Стало.** `docker/agent/Dockerfile`: `python:3.11-slim`, git, ripgrep, codegraph, beads и dolt — закреплённых версий с контрольными суммами, как в образе сервера; пользователь `agent` (uid 1000); `/workspace`; `CMD sleep infinity`. Самого Grid в образе нет, контекст сборки — только эта папка:

```
docker build -t grid-agent:latest docker/agent
```

Старый образ сохранён под тегом `grid-agent:sandbox-2026-09-20`. Контейнеры, созданные из старой сборки, пересоздаются на новой при следующем входе пользователя.

## 7. Docker Desktop на Windows

В режиме Hyper-V каждая новая папка монтирования требует подтверждения File sharing, а у каждого пользователя своя `users/<id>/workspace`. Правка `settings-store.json` при работающем Docker не применяется. Решение — один раз: **Settings → Resources → File sharing → добавить `C:\Users\danii\.grid\web` → Apply & restart**, либо перейти на WSL2.

## 8. Что осталось

| Риск | Где | Комментарий |
|---|---|---|
| На Linux контейнер работает в `network_mode: host` | `ContainerManager._create_container` | Команды пользователя видят сервисы хоста на `127.0.0.1`, включая сам Grid. Нужна отдельная сеть с доступом к прокси. |
| Обход через `dir_fd` недоступен на Windows-хосте | `utils/confined_fs.py` | Действует только проверка пути. Ссылки из Linux-контейнера на путях Windows не работают, но гарантия слабее. |
| Гонка при перечислении имён | `os.walk` в инструментах поиска и списка файлов | Раскрываются только имена файлов, не содержимое. |
| Общий `verbose.log` | `utils/logger.py` | Логи ходов разделены по пользователям, подробный лог — один на сервер. |
| Из git-инструментов помечен только `git_log` | `tools/git_tools.py` | Остальные git-инструменты с аккаунтами не выдаются, пока их не проверят и не пометят. |
