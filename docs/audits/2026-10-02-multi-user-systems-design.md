# Многопользовательская работа, артефакты и библиотека систем

Дата: 2026-10-02. Проверена рабочая копия `/root/grid`, HEAD `3110b30`, включая существующие незакоммиченные изменения. Это архитектурный аудит и план реализации, не отчёт об исправлении кода. Изменения других авторов сохранены.

## Вывод

Основа уже существует: аккаунты, контейнер на пользователя, защищённое скачивание файлов, личные системы, builder и административная публикация. Главные пробелы — сетевые границы контейнеров, надёжность жизненного цикла, версии результатов и отсутствие публикации приватных builder-систем. Расширять общую библиотеку следует после устранения этих проблем.

Для первой версии предлагается: пользователь строит приватную систему, тестирует её, отправляет неизменяемую версию на проверку, после одобрения она появляется в библиотеке. Другой пользователь устанавливает конкретную версию в своё пространство. Публикация не должна автоматически включать систему в маршрутизацию всех пользователей.

## Текущая архитектура

- `web_chat/space.py`: отдельные workspace, история и SQLite-сессии пользователя. Служебные данные лежат вне доступного агентам workspace. В режиме accounts контейнер обязателен, кроме явно доверенного режима.
- `core/managers/container_manager.py`: один контейнер на пользователя, bind mount workspace, пользователь agent, лимиты CPU/RAM/PID, отключённые capabilities, no-new-privileges. Все чаты и агенты этого пользователя делят контейнер и файлы.
- Инструменты выполняются неодинаково: shell/git/MCP — в контейнере; файловые инструменты — в серверном процессе с ограничением путей; builder — в серверном процессе с доступом к разрешённому хранилищу систем.
- `web_chat/uploads.py`: авторизованный download из своего workspace, покомпонентный обход через dir_fd/O_NOFOLLOW, отказ для специальных файлов, attachment и no-store. Это полезная существующая защита, её нужно сохранить.
- `web_chat/user_systems.py`: системы `mine` из разрешённых шаблонов, с отправкой администратору.
- `core/system_store.py`: приватные builder-системы `built` с конфигами, skills и пакетами инструментов; shared-системы администраторов. Один статус published означает разные вещи: приватную активацию либо общую публикацию.
- `web_chat/system_hub.py`: общая публикация сейчас добавляет систему в маршрутизацию; пользовательского механизма установки закреплённой версии библиотеки нет.

Дополнительные выводы по коду:

- Download зависит от `current_space`, то есть создание пространства может потребовать запуска Docker. При недоступности Docker пользователь может потерять HTTP-доступ к уже готовым файлам. Авторизация скачивания должна обращаться к хранилищу артефактов без старта runtime.
- `require_quality` — opt-in: отсутствие контракта и отметки contract-required разрешает публикацию. Это явно предусмотренная совместимость, но для новых общественных пакетов нужна обязательная отдельная политика публикации.
- Установка pip-зависимостей происходит до отключения сети. Подготовка зависимостей — самостоятельное выполнение недоверенного кода, её нельзя считать безопасной только из-за последующего offline-теста. Нужен build sandbox без пользовательских данных и ключей, ограниченный доступ к источникам пакетов, закреплённые транзитивные зависимости и хеши.
- Общий workspace внутри пользователя — осознанная текущая модель, но параллельные чаты/агенты могут перезаписывать результаты друг друга. Контейнер на пользователя не обеспечивает изоляцию задач.

## Безопасная передача результатов

Разделить рабочие файлы и опубликованные результаты. Файловый браузер workspace остаётся приватным инструментом владельца; карточки результатов в чате ссылаются на ArtifactVersion, а не на живой путь.

Предлагаемые сущности: Artifact(id, owner_id, project_id), ArtifactVersion(id, artifact_id, run_id, agent_id, original_path, name, size, sha256, blob_key, created_at). Хранилище blob недоступно для записи из контейнера; метаданные и права находятся в серверной БД. Хеш не является разрешением на чтение.

Поток: агент создаёт/правит файл → запрашивает создание результата → сервис безопасно открывает файл в разрешённом workspace → формирует завершённый снимок с лимитом размера → атомарно сохраняет blob и метаданные → UI получает карточку со скачиванием и историей версий.

Гарантии:

- Пользователь может сам выбрать файл для выдачи. Автоматическое обнаружение изменённых файлов предлагает кандидатов, но не публикует весь workspace: там могут находиться секреты и промежуточные данные.
- Никаких произвольных абсолютных путей сервера. Сохранить обход через FD без symlink, разрешать только regular files; для пакетов/архивов запретить traversal, symlink/hardlink и специальные записи, ограничить количество и суммарный размер распаковки.
- Снимок нельзя считать атомарным по одной проверке mtime или fstat до/после. Для сильной гарантии нужен snapshot файловой системы либо остановка всех писателей на момент экспорта. Более простой контракт: агент завершает запись через temporary+rename, сервис копирует в собственное хранилище, проверяет изменения и отказывает при конкуренции; этот контракт слабее против злонамеренного писателя.
- `GET /api/artifacts/{version_id}/download`: проверка владельца/ACL на каждый запрос; непрозрачный id сам по себе доступа не даёт. Готовые файлы доступны при остановленном runtime. Attachment, nosniff, корректная длина из immutable blob; Range для больших файлов.
- Preview HTML/SVG/документов — отдельный origin без сессионных cookies, изолированный рендерер; не отдавать активный пользовательский контент inline с origin приложения.
- Публичная ссылка — отдельное явное действие с TTL и отзывом. Для object storage короткоживущая signed URL только после проверки доступа. Пересланная приватная ссылка не должна открывать чужой файл.
- Запись артефакта идемпотентна; квота резервируется транзакционно. Удаление метаданных, retention и garbage collection учитывают незавершённые загрузки и общие ссылки.

Карточка результата показывает имя, размер, автора-агента, запуск, время, версию; для изменённого текста — diff и скачивание прежней версии. Это закрывает сценарий «агенты создали или исправили файлы», включая файлы вне Git и бинарные документы.

## Построение и общая библиотека систем

Единая модель: System(owner, visibility), SystemRevision(immutable manifest + content digest), Installation(user/project, revision, granted_permissions), Submission(revision, state, review). Развести visibility, состояние проверки, доступность версии и локальную активность маршрутизации.

Жизненный цикл: private draft → test → frozen revision → submitted → approved/published → installed → locally active. Отдельные declined/withdrawn/revoked; отзыв публикации не стирает историю запусков и авторство. При срочном security revoke новые старты запрещаются, политика остановки текущих запусков задаётся явно.

- Конструктор разрешает роли агентов, entrypoint, граф делегирования, модели из доступного каталога, skills и sandbox-пакеты. Проверяет несуществующие узлы, недостижимые роли и лимиты. Циклы допустимы только с ограничением глубины/вызовов/времени и общего бюджета.
- Один пакет должен переносить конфиг, prompts/skills, инструменты, lock зависимостей, декларацию разрешений, тесты, совместимость runtime и образа. Исключить workspace, чаты, логи, пользовательские ключи и локальные абсолютные пути. Провайдеры представлены идентификаторами, секреты связываются при установке.
- Submission фиксирует весь пакет и базу; изменение черновика создаёт новую ревизию. Одобрение и результаты тестов привязаны к digest пакета плюс окружению проверки. Нельзя подменить файлы после проверки.
- Публичный пользовательский код остаётся недоверенным даже после модерации: только sandbox, без host Python imports и произвольных host MCP-команд. Рабочий, тестовый и evaluation-профили должны следовать одной политике безопасности.
- Перед публикацией: схема/граф/права, отсутствие секретов, обязательные smoke и acceptance-тесты, лимиты времени/ресурсов, независимые от автора проверки. Успешные тесты не являются доказательством безопасности.
- Библиотека: карточки с автором, версией, назначением, входами/выходами, примерами, разрешениями и результатами проверок. Установка/fork/обновление/rollback — отдельные действия. Расширение разрешений при обновлении требует нового согласия; установленная версия сама не меняется.
- Обычный пользователь должен видеть безопасную публичную карточку: нынешняя admin-only detail для shared created-system не подходит библиотеке. Административные конфиги, секреты и индивидуальная статистика запусков не входят в публичный API.

## Многоагентная работа

Граница безопасности — пользователь/проект; граница конкурентных изменений — запуск. Для независимых задач предпочтительны отдельные workspace/worktree либо snapshot overlay. Совместную работу над одним деревом делать явной: список назначенных файлов, блокировка/контроль версии записи, обнаружение конфликтов и интеграционный шаг. Git worktree помогает с merge, но сам по себе не изолирует выполнение кода.

Идентичность выполнения: tenant/project/conversation/system_revision/agent/run. Родитель и все делегаты разделяют общий бюджет токенов, стоимости, времени, процессов и тестовых запусков. Лимита числа пользовательских сообщений недостаточно. Планировщик обеспечивает справедливость между пользователями и ограничивает суммарное потребление сервера.

UI показывает дерево задач, зависимости, состояния queued/running/waiting/completed/failed/cancelled, результаты и конфликты. Stop распространяется на потомков и реальные процессы; «остановлена coroutine» не означает «остановлена команда в контейнере». Resume не повторяет бездумно действия с неизвестным исходом.

## Проверка и ограничения

Выполнено: `.venv/bin/python -m pytest -q tests/test_container_manager.py tests/test_web_uploads.py tests/test_system_hub.py tests/test_system_builder.py tests/test_web_spaces.py` — 98 тестов прошли, одно предупреждение о deprecated httpx-интеграции Starlette. Это существующие тесты; прохождение не закрывает описанные сценарии.

Дополнительно: воспроизведены изменение размера открытого файла; запуск describe/test после смоделированного отказа network disconnect; пересечение двух SDK-сессий и удаление данных cleanup; реальный отказ chown в временном Docker-контейнере с cap_drop ALL и network none, без host mounts, удалённом через --rm. Не проводились атаки на рабочие сервисы, нагрузочные испытания и полный end-to-end прогон публикации.

Runtime-код не изменён. План не зарегистрирован в Beads: `bd prime` завершился `bd: command not found`. Этот документ — результат аудита, а не замена трекера; при доступном bd этапы и дефекты следует оформить как связанные задачи.

Внешняя сверка: [Docker host network](https://docs.docker.com/engine/network/drivers/host/) подтверждает общий network namespace; [bridge](https://docs.docker.com/engine/network/drivers/bridge/) описывает связь контейнеров одной сети; [rootless](https://docs.docker.com/engine/security/rootless/) и [user namespaces](https://docs.docker.com/engine/security/userns-remap/) — варианты дополнительного снижения привилегий. Rootless/userns требуют отдельной проверки UID/GID bind mounts; это усиление, а не замена сетевой политики и ACL.
