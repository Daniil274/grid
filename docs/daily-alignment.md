# Ежедневные рекомендации по чатам и проектам

## Статус и область

Реализован встроенный **opt-in**, без LLM и без вызова агентов, анализатор `web_chat/digest.py`.
В этой поставке проверены только **синтетические** данные. Live-сервис из среды реализации
недоступен, включение для реальных пользователей **не выполнено**. В
`/user/daily-alignment/VERIFICATION.md` сохранён исторический FAIL до реализации и добавлена
проверка V28 с тремя дефектами. Исправления и собственные offline-регрессии описаны в
`/user/daily-alignment/FIX.md`; это не независимая приёмка исправлений.

Это минимальный, намеренно узкий анализ:
- текстовые сообщения `user` / `assistant` из `space.context_manager().conversation_views()`;
- проекты, в том числе изменение описания/заметок/архивности, из `space.project_snapshot()`;
- сигнал коррекции в пользовательском тексте: `incorrect`, `wrong`, `instead`, `исправь`,
  `неверно`, `ошибка`, `вместо` (точные слова, без учёта регистра);
- отсутствие описания у активного проекта.

Рекомендации предлагают человеку проверить эпизод / уточнить требование или цель проекта.
В каждом выводе раздельно даны наблюдение, **гипотеза** и предлагаемое действие, цитата,
conversation/project ID, timestamp, нулевой индекс сообщения в сохранённом чате и SHA-256
от версии правил/содержимого. Для проекта есть ID и title. Индекс относится к состоянию
чата в момент анализа: после удаления/перестановки сообщений проверяйте также timestamp,
цитату и fingerprint. Отсутствие коррекций **не интерпретируется как удовлетворённость**.
Это не семантическая оценка всех диалогов и не автоматическое обучение.

Вложения, мультимодальные сообщения, tool/system сообщения, файлы workspace, память,
инструкции, plan board и внешние источники не анализируются. Это указано в `scope` отчёта;
неподдерживаемые сообщения и исключённые роли посчитаны отдельно. Нет автоматического
изменения проектов, памяти, промптов или инструкций. Чистая функция `analyze()` получает
только неизменяемые текстовые Episode, не UserSpace, агентский factory или tools.
Текст пользователя — данные, а не команды. Провайдеры и API-ключи этому анализатору не нужны.

## Интеграция и изоляция

Используется существующий lifecycle `WebChatServer` и `SpacePool.use(user.id)`, а не новый
планировщик ОС или headless-агент с полным набором инструментов. Если задан существующий
`lazy_path`, рядом открывается `daily-digest.db`; оба стандартных launcher пути уже передают
`lazy_path`:
- single-user: `<deployment.config.get_logs_directory()>/daily-digest.db`;
- accounts: `<data-dir>/daily-digest.db`.

Для программного `WebChatServer` без `lazy_path` функция не подключается (API вернёт 404).
Для подключения передайте `lazy_path=Path(<persistent-state>)/"lazy.db"`. Сервер должен
иметь право записи в эту директорию. Стандартный launcher изменять не требуется.

В БД всегда используется составной ключ с user_id. API берёт ID **только** из существующей
аутентификации `current_user`; ID в query/body не выбирает пользователя. Перед чтением
дополнительно проверяется `space.user_id`. У отключённых пользователей даже не запрашивается
space. Scheduler не перечисляет аккаунты/переписки: он обрабатывает только opt-in записи;
disabled/deleted accounts отсекаются существующим server `may_resume`.
БД содержит приватные цитаты разных пользователей: это серверное хранилище вне workspace,
не передавайте файл агентам/клиентам. ОС-права и backup должны быть такими же, как для lazy.db.

## Подключение к реальному runtime — оператором

1. Установите этот код **в существующий сервер**, сохранив его обычные config/routing,
   accounts/data-dir, прокси и идентификацию. Не запускайте новую пустую single-user среду
   вместо рабочего хранилища. Перезапустите обычный процесс `python -m web_chat ...` с его
   прежними аргументами (CLI: `python -m web_chat --help`).
2. Убедитесь, что стандартный launcher передаёт persistent `lazy_path` (пути выше).
   Никакой пользователь пока не включён. Не подменяйте ID и не копируйте чужую историю.
3. Войдите **как нужный пользователь** в обычном браузере и откройте консоль на той же
   origin, где открыт чат. Сначала проверьте исходное состояние:

   ```javascript
   await (await fetch('/api/daily-digest')).json()
   // settings.enabled: false; runs: [] для первого подключения
   ```

4. Явно включите только текущего пользователя, задав время и лимиты:

   ```javascript
   await (await fetch('/api/daily-digest/settings', {
     method: 'PUT', headers: {'Content-Type': 'application/json'},
     body: JSON.stringify({enabled: true, hour_utc: 3, max_records: 200,
                           max_chars: 64000, max_record_chars: 8000})
   })).json()
   ```

   PUT заменяет настройки целиком; пропущенные поля берут defaults. Допустимые диапазоны:
   `hour_utc` 0..23, `max_records` 1..2000, `max_chars` 1000..1000000,
   `max_record_chars` 100..262144 (прежние настройки до 32000 остаются допустимыми).
   Неверные типы/неизвестные поля — HTTP 422.
   `enabled` должен быть JSON boolean, не строкой.

5. Первый контролируемый live-прогон (можно до заданного часа):

   ```javascript
   const run = await (await fetch('/api/daily-digest/run', {method: 'POST'})).json();
   console.log(run);
   const history = await (await fetch('/api/daily-digest')).json();
   console.log(history);
   ```

   Проверьте user_id, evidence IDs и цитаты в **своём** UI истории чатов/проектов, `coverage`,
   `pending`, ошибки/диагностику. Запишите факт активации только после этого live-прогона.
   Здесь такой шаг **не исполнялся**. Нет необходимости выдавать shell доступ или LLM-ключ.

6. Для ежедневности оставьте основной web_chat сервер работающим под его обычным
   supervisor/systemd/container restart policy. Отдельный cron **не нужен**. Каждые 60 секунд
   цикл проверяет opt-in пользователей. Не раньше `hour_utc`, один отчёт на текущую **UTC**
   дату; после рестарта позднее этого часа — догоняющий запуск сегодня. Пропущенные даты
   не создаются задним числом, но необработанные эпизоды остаются для следующего анализа.
   Это UTC, без локального timezone/DST. Ручной POST тоже занимает текущую UTC дату.

В multi-user cookies передаёт обычный same-origin браузер. Не используйте тестовый
`X-Test-User`: в продукте такого способа входа нет. Запросы изменения защищены существующим
OriginGuard; внешняя origin должна быть разрешена обычной настройкой сервера, не обходом guard.

## Отчёты, инкрементальность и повторы

`GET /api/daily-digest` показывает settings и последние 31 run (БД сохраняет всю историю).
У run есть `day`, `attempts`, `next_try` (Unix UTC), `error`, `diagnostics`, `report`.
Успешный `report` содержит findings, scope, limits и coverage:
- число чатов/проектов, исключённые собственные отчёты (`metadata.daily_digest`), роли;
- `available_text_records`, `unchanged`, `processed`, `processed_chars`;
- `pending`, `oversized_pending`, `unsupported_messages`, `errors`.

Лимиты относятся к **входу анализатора**, а не к числу ссылок в инвентаризации. Инвентаризация
использует существующие in-process conversation_views (все сообщения уже загружены самим
ContextManager); fingerprint требует прохода по текстам. Это не ограничитель размера исходной
БД/памяти сервера. Ни исходные чаты, ни сообщения не копируются в отчёт целиком.

Успешный отчёт и hashes обработанных эпизодов сохраняются **одной SQLite транзакцией**.
Создание/удаление чата не связано с успехом анализа: отчёты не пишутся в чат и его удаление
не удаляет ledger. Нет автоочистки отчётов/seen и отдельной кнопки сброса.
Повторный POST/тик в тот же день возвращает `already_done` и тот же отчёт. Новые сообщения,
редактирование текста/проектов после успеха попадут в **следующий UTC день**; force-reset
на тот же день специально отсутствует. Неизменённые эпизоды повторно не анализируются.
Индексы и содержание являются версией эпизода; перестановка/удаление сообщений может привести
к повторной проверке изменившихся позиций, а не к утверждению, что это новая беседа.

Очередь `digest_pending` хранит порядок первого обнаружения необработанных ключей отдельно
для каждого пользователя. Ожидающие эпизоды (включая проекты) идут перед новым притоком,
даже после рестарта; правка ожидающего эпизода не сбрасывает его место. Очередь, hashes и
отчёт коммитятся вместе; удалённые/вернувшиеся к уже обработанной версии ключи убираются.
Таблица добавляется автоматически к прежнему ledger без сброса settings/seen/reports.
Первый порядок при обновлении — порядок текущей инвентаризации, далее сохраняется FIFO.
Для конечного числа предшественников и записи, помещающейся в оба символьных лимита,
успешные дневные запуски обеспечивают продвижение даже при непрерывном новом притоке.

Усечений цитаты не следует путать с усечением входа: слишком большой текст не обрезается для
анализа и **не помечается обработанным**. Он остаётся `oversized_pending`; увеличьте лимит
(в пределах диапазона) или примите явно неполное покрытие. Другой backlog по числу/сумме
символов обрабатывается в следующие дни; `partial` не означает покрытие всех чатов.
Мультимодальные сообщения остаются неподдерживаемыми, не превращаются в «успешно прочитанные».

Defaults не увеличены: `max_record_chars=8000`, `max_chars=64000`. Для максимальных
проектных notes 32768 символов настройте, например, `max_record_chars=262144` и
`max_chars=1000000`: учитывается **полный JSON проекта**, а не только notes. Верхний лимит
покрывает также экранирование управляющих символов (`\u0000` занимает 6 символов) и
максимальное описание. Если целая запись не помещается в `max_chars`, одной настройки
`max_record_chars` недостаточно; такая запись остаётся pending и не блокирует меньшие.

### Ошибки и эксплуатация

- Ошибка чтения любого источника не публикует успешный отчёт и не продвигает ни один hash.
  `diagnostics.errors` содержит source/code, без текста исключения/секретных путей.
  Временный отказ одного источника задерживает весь дневной snapshot — осознанный компромисс
  минимального контура, а не скрытая потеря данных.
- Проекты читаются напрямую через strict `ProjectStore.read_snapshot` по пути своего
  UserSpace, без создания lazy ProjectStore, mkdir, lock-файлов, recovery или переименований.
  Атомарная публикация project store через replace даёт целый файловый snapshot; кэш другого
  worker не используется. JSON/Unicode/I/O/schema errors дают `project_read_failed`.
  Отсутствующий файл означает пустой inventory, кроме известного failed-load уже созданного
  UI store (например, файл ранее перемещён его recovery). В этом случае нужен ремонт
  источника, а не ложный complete. Штатное recovery UI store не менялось; digest его не вызывает.
  Старые embedded adapters без `project_snapshot()` используют прежний `project_store.list()`
  и должны сами обеспечивать read-only и исключения при ошибках чтения.
- Сбой анализа/записи отчёта откатывает все hashes. Ошибка открытия user space записывается
  как `space_unavailable`. Исключения не выводят содержимое сообщений/секреты в лог.
- Максимум **4 попытки за UTC день**, пауза после ошибки: 15, 30, 45, 60 минут.
  POST до next_try или после исчерпания бюджета возвращает `backoff`, не сбрасывая бюджет.
  После временной ошибки повторите POST после next_try или дождитесь тика. Состояние ошибок
  и попыток переживает restart. На следующий день бюджет возобновляется, progress не теряется.
- При process kill незавершённая транзакция откатывается; незавершённая попытка может быть
  повторена. При недоступности самой БД нельзя надёжно записать retry budget — цикл пробует
  снова не чаще следующего 60-секундного тика и пишет общий warning; данные не помечаются.
- SQLite `BEGIN IMMEDIATE` сериализует несколько worker-процессов, RLock защищает соединение,
  async lock исключает параллельные ручные вызовы в одном сервисе. Внешний долгий lock БД
  может вызвать временный отказ (timeout 1 секунда), но не дубли/двойное продвижение.
- Анализ не занимает агентский turn: busy headless-агента не требуется ожидать. Чтение
  ContextManager использует его штатные lock/snapshot; lock timeout — обычная ошибка чтения
  с ограниченными повторами. Не выполняется параллельная агентская правка.
- Если `runs` пуст и настройка enabled — проверьте часы UTC, доступность сервера и ожидаемый
  user_id, затем POST. При 404 — проверьте lazy_path и наличие новой версии кода. При 401/403
  — вход/origin, а не попытка заменить user_id в запросе.

Отключение (не удаляет историю и не меняет исходные данные):

```javascript
await fetch('/api/daily-digest/settings', {
  method: 'PUT', headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({enabled: false})
});
```

Не удаляйте общую daily-digest.db ради одного пользователя: там состояние других пользователей.
Backup/retention/удаление данных выполняйте штатной серверной политикой вне пользовательского
workspace и при остановленном процессе. Удаление ledger сбросит инкрементальность и opt-in.

## Проверки без live

Отдельное окружение (существующую `.venv` не менять):

```sh
cd /user/grid
python3 -m venv .grid/venv-daily
.grid/venv-daily/bin/python -m pip install -e '.[dev]'
PYTHON_DOTENV_DISABLED=1 .grid/venv-daily/bin/python -m pytest -o addopts='' \
  -p no:cacheprovider --basetemp=.grid/pytest-kbs \
  tests/test_daily_digest.py tests/test_lazy_runner.py tests/test_lazy_service.py \
  tests/test_web_space.py tests/test_web_spaces.py tests/test_web_accounts.py \
  tests/test_web_ui_routes.py tests/test_projects_store.py tests/test_projects_api.py
.grid/venv-daily/bin/python -m ruff check web_chat/digest.py tests/test_daily_digest.py
```

`PYTHON_DOTENV_DISABLED=1` не даёт тестовому импорту существующего agent_factory читать `.env`.
Это только настройка offline-тестов, не инструкция выключать штатные credentials live-сервера.
Тесты используют временные БД, fake SpacePool, а один тест — настоящий ContextManager и
WebChatServer с поддельными данными и тестовым identify. Ничто из этого не является live
результатом. Проверяются изоляция, guard/auth, repeat/restart, concurrent workers, atomic
publication failure, interruption, budget/backoff, source errors, settings, лимиты/backlog,
инкрементальность сообщений/проектов, отсутствие возможностей изменения у анализатора.
Регрессии V28 также проверяют реальный read-only snapshot (без recovery), FIFO при постоянном
притоке и рестартах, rollback очереди, upgrade ledger и максимальные notes с JSON-экранированием.
