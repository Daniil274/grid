# Инструменты lazy-задач для агентов

Агент видит и меняет фоновые задачи пользователя прямо из чата, не открывая страницу `lazy.html`.
Инструменты — тонкая проверяющая обёртка над тем же сервисом (`web_chat.lazy.service.LazyAgents`),
что и страница: планировщик, хранилище и запуск шагов остаются его собственными.

| Инструмент | Что делает |
|---|---|
| `lazy_catalog()` | из чего состоит задача здесь: агенты и подписки (с проблемой доступности), размеры, приоритеты, состояния, лимиты, какие поля можно менять |
| `lazy_list(include_finished=false, project_id="", limit=20)` | задачи, новые первыми: `id`, заголовок, состояние, `steps.done/total`, следующий шаг, дедлайн, `version` |
| `lazy_get(task_id)` | одна задача целиком: бриф, приёмка, шаги с причинами, последние 5 событий истории, размещение на плане |
| `lazy_preview(...)` | где такая задача встанет среди существующих — **ничего не сохраняет и ничего не запускает** |
| `lazy_create(..., status="active")` | создаёт задачу; `request_id` делает повтор идемпотентным, `status="paused"` создаёт её уже на паузе; `not_before` — момент релиза, `repeat` — типизированное правило повтора, `cap` — недельный предел задачи (не указан = без предела) |
| `lazy_update(task_id, ...)` | меняет только названные поля; `series=true` — открытый раунд серии; `expected_version` защищает от устаревшей правки; `not_before=""` снимает релиз |
| `lazy_cancel(task_id, series=false)` | отменяет задачу; с `series=true` — серию и все следующие раунды |

Удаления среди инструментов нет намеренно: отмена — это штатное завершение, а не стирание истории.

## Правда о запуске шагов

Формулировка «инструмент не запускает шаги» верна только наполовину, и вторая половина важна:

- Вызов инструмента **не ждёт** ни одного шага и не считает план сам.
- Но `lazy_create`, `lazy_update` и `lazy_cancel`, как и API страницы, **сохраняют задачу и будят цикл сервиса**
  (`LazyAgents.wake`, `web_chat/lazy/service.py:147`). Проснувшийся цикл (`_loop`/`_tick`, `service.py:168`, `:180`)
  пересчитывает план и запускает шаг, если тот по плану уже наступил (`service.py:194`, `:196`).
- Планировщик ставит шаг **как можно раньше**, в пределах бюджета и (по умолчанию) так, чтобы шаг успел
  закончиться до начала часов пользователя (`core/lazy/planner.py`, `search`). Поэтому активная задача,
  созданная в подходящее окно при наличии места, обычно подхватывается в течение одного тика — это настоящий
  фоновый запуск модели, а не «примерка».
- **Дедлайн в будущем работу не держит.** `deadline` говорит, когда задача должна быть готова, а не когда ей
  можно начаться: активная задача с местом стартует сразу. Держит работу `not_before` — момент релиза,
  раньше которого планировщик не ставит ни один шаг, даже если место есть (`Wait("not_before")`).

Практические следствия для агента:

- `lazy_preview` — единственный вызов, который гарантированно ничего не сохраняет и не запускает.
- `lazy_preview` не пишет ничего вообще — ни задачи, ни строки настроек первого визита
  (`settings_for(..., persist=False)`), поэтому его эффект честно объявлен `read`.
- `lazy_create` — не preview. Если пользователь хочет сначала посмотреть, покажи `lazy_preview`
  и спроси подтверждение; если просит «подготовь, но не начинай» — создай с `status="paused"`:
  задача сохраняется уже на паузе одним атомарным сохранением и не становится eligible вовсе.
  **Не** создавай активную задачу и не ставь её на паузу вторым вызовом: между двумя вызовами
  цикл может успеть запустить первый шаг, и обещание «ничего не началось» будет ложью.
- `lazy_update` с `status="active"` (снятие с паузы), `run_now=true` или сдвинутым дедлайном тоже может
  запустить ближайший шаг сразу.
- `lazy_cancel` будит цикл, но только чтобы убрать задачу из плана; идущий шаг получает просьбу остановиться
  на безопасной точке (`_stops`), новый не начинается.

Тик по умолчанию — не дольше 300 с (`TICK`), плюс просыпание по событию; «сразу» здесь означает
«в пределах тика», а не «синхронно внутри вызова инструмента».

## Порядок работы

1. `lazy_catalog` — понять, на какой подписке и какими агентами задача вообще может идти
   (`problem` у агента означает, что он сейчас недоступен).
2. `lazy_list` → `lazy_get`: что уже есть, в каком оно состоянии и какая у него `version`.
3. `lazy_preview` для новой задачи: шаги, на которые она разобьётся, и кого она подвинет.
4. `lazy_create` (с одним `request_id` на одну задуманную задачу) или `lazy_update`/`lazy_cancel`
   с `expected_version` из последнего чтения.

## Идемпотентность создания

`request_id` — ключ вызывающего на одну задачу. Повтор с тем же ключом (таймаут ответа, повторный ход,
два вызова в одном ответе) возвращает уже созданную задачу: `created=false`, `status="exists"` и подсказка
прочитать её через `lazy_get`. Поиск и вставка идут под одной блокировкой (`_create_lock`), поэтому гонка
одного процесса не даёт двух копий; последнее слово за хранилищем — `LazyStore.save_new_task` вставляет
задачу в одной транзакции (`BEGIN IMMEDIATE`) и под уникальным ключом `(user_id, request_id)`, так что
две копии не появятся и между процессами (второй сервер на том же `lazy.db`). Проигравший получает
`False` и читает задачу победителя. Без `request_id` каждый вызов создаёт новую задачу — как и раньше на странице.
Ключ хранится в самой задаче (`Task.request_id`) и проверяется по пользователю: чужой ключ ничего не находит.

## Серия повторов: релиз раунда, а не только дедлайн

Задача с `repeat_hours > 0` или с календарным `repeat` — серия: все раунды делят один `series_id`
(у первого раунда это его собственный `id`), следующий раунд наследует `series_id` и `project_id`.
Поэтому «останови ежедневный отчёт» адресует серию, а не случайно открытый раунд:

- `lazy_update(..., series=true)` правит открытые раунды серии — следующий раунд делается из них;
- `lazy_cancel(..., series=true)` отменяет открытый раунд и не создаёт следующий; завершённая серия отвечает
  `status="finished"` и ничего не меняет;
- `task_id` в этих вызовах может быть `series_id` из ответов `lazy_list`/`lazy_get`.

Следующий раунд получает **релиз** (`Task.not_before`), а не только сдвинутый дедлайн. Момент релиза считается
от конца предыдущего раунда (`web_chat.lazy.service._next_round`):

| правило | релиз |
|---|---|
| `interval` (`repeat_hours`, или `{"kind": "interval", "hours": 6}`) | целый период после релиза предыдущего раунда — на той же сетке, без дрейфа от длительности раунда |
| `daily` (`{"kind": "daily", "time": "04:00"}`) | ближайшие 04:00 по местному времени пользователя после конца раунда |
| `weekly` (`{"kind": "weekly", "time": "04:00", "weekday": "mon"}`) | ближайший названный день недели, то же местное время |

Свойства, на которые можно опираться:

- **Два раунда никогда не идут подряд**: релиз всегда строго позже конца предыдущего раунда; короткий раунд
  ждёт полный период, длинный пропускает пропущенные слоты.
- **Пропущенное не догоняется очередью**: если слот (или несколько) прошёл, пока раунд работал или сервер был
  выключен, будет один раунд — на ближайшем будущем слоте, а не пачка пропущенных. Политика названа явно:
  `missed: "skip"` в DTO правила.
- **DST детерминирован**: несуществующее местное время (весенний разрыв) сдвигается вперёд на величину разрыва
  (02:30 → 03:30), неоднозначное (осенний откат) берётся первым вхождением (`fold=0`). Одинаковый ответ на
  каждом прогоне; часовой пояс — IANA-имя, чужой/выдуманный отвергается (`invalid`), а не читается как UTC.
- **Дедлайн раунда** сохраняет тот же промежуток после релиза, что был у предыдущего раунда между его релизом
  и дедлайном.
- Первый раунд серии релиза не имеет (`not_before=None`): он стартует, как только позволяет план.

## Контракт расписания, релиза и бюджета (для UI и Builder)

Типизированные поля задачи (`core/lazy/model.py`, `core/lazy/schedule.py`):

```jsonc
{
  "not_before": 1794129600.0,          // релиз, epoch seconds; null = как позволит план
  "deadline":   1794292800.0,          // когда должно быть готово; будущий дедлайн ничего не держит
  "repeat": {                          // правило серии; null — задача разовая
    "kind": "daily",                   // "interval" | "daily" | "weekly"
    "time": "04:00",                   // для daily/weekly — местное время
    "timezone": "Europe/Moscow",       // IANA; чужой отвергается
    "missed": "skip"                   // пропущенные слоты не догоняются
  },
  "cap": 12.5                          // недельные пункты задачи/серии; null = без своего предела, 0 = реальный ноль
}
```

Правило `interval` в этом виде: `{"kind": "interval", "seconds": 21600, "hours": 6, "missed": "skip"}`;
`repeat_hours` остаётся его короткой формой и очищает календарное правило (одно расписание за раз).
Поле `repeat` у инструментов принимает либо число часов, либо JSON-объект выше.

Ответы (`lazy_list`, `lazy_get`) дают момент **двумя способами** и с именем зоны — сравнивать удобно epoch,
читать человеку и календарю — ISO:

```jsonc
"not_before": 1794129600.0,
"times": {
  "not_before": {"epoch": 1794129600.0, "iso": "2026-11-08T04:00:00+03:00", "timezone": "Europe/Moscow"},
  "deadline":   {"epoch": 1794292800.0, "iso": "2026-11-10T04:00:00+03:00", "timezone": "Europe/Moscow"}
}
```

`lazy_get` кладёт те же моменты в `placement.times` (`scheduled_release`, `next_start`, `finish_at`).
Разделение намеренное:

- `scheduled_release` — когда раунд **имеет право** начаться (релиз, `not_before`);
- `next_start` — где он **окажется** по плану с учётом квоты, часов пользователя и занятости раннера;
- `deadline` — когда он должен быть готов.

Инвариант: `scheduled_release <= next_start`. Точный старт в момент релиза не обещается: при нехватке квоты
`next_start` сдвинется, а причина будет в `wait` (`not_before`, `budget`, `my_hours`, `busy`, `after_step`,
`retry`, `cap`, `paused`).

### Бюджет серии

`cap` — недельные пункты **серии**, а не раунда: считается по ledger прогонов
(`LazyStore.runs`, `_seven_day` из `Run.used`) за фиксированное скользящее окно в семь суток, кончающееся
«сейчас» (`SERIES_WINDOW` в `web_chat/lazy/service.py`). Новый раунд не открывает новый бюджет, и сброс
квоты провайдера на него не влияет. Задача без серии, как и раньше, считает свои закрытые шаги.

- `cap` не указан / `null` — своего предела нет; доли пула и комнаты окон действуют как обычно;
- `cap: 0` — настоящий ноль: любой шаг дороже нуля блокируется с `wait.code == "cap"`, молчаливого повышения нет.

Бюджет пула (`allowances`) задачу не трогает: `cap` — её собственный предел сверх общей доли.

### Форма создания на странице

Правило строит `web_chat/js/lazy/repeat.js` (`repeatPayload`), форму — `web_chat/js/lazy/dialogs.js`:

- «Once» — `repeat_hours: 0`, `repeat: null`;
- «Own interval» — `repeat_hours: <часы>`, календарного правила нет;
- «Every day» / «Every week» — `repeat: {kind, time: "HH:MM", timezone, weekday?, missed: "skip"}` и
  `repeat_hours: 0`. Время строго `HH:MM`, зона — IANA (по умолчанию зона пользователя из настроек);
  неизвестная зона или кривое время не отправляются, а показываются ошибкой. День недели есть только у weekly;
- «Start no earlier than» — `not_before` (момент; можно не задавать). Подпись прямо говорит: это релиз,
  а дедлайн — когда готово;
- «Own weekly budget» — пусто → `cap: null` (своего предела нет), `0` → `cap: 0` (настоящий ноль).

Карточка задачи показывает правило словами (`describeSchedule`: «Every 6 h», «Daily at 04:00
(Europe/Moscow)»), релиз («Released …», пока он в будущем) и свой бюджет, когда он задан. Превью формы
показывает `scheduled_release` отдельной строкой («Released … - no step starts before it»), а ожидание
приходит как `wait.code == "not_before"`. Надпись «Deadline» относится только к готовности.

Релиз нельзя обойти: `run_now` меняет порядок и часы, но не `not_before`; `preview` показывает релиз и
ничего не сохраняет; страница и `lazy_update` хранят `not_before` отдельным полем.

## Защита от устаревших изменений

`lazy_get` (и `lazy_list`) отдают `version`. Передай её как `expected_version` в `lazy_update`/`lazy_cancel`:
если задачу успели изменить (шаг отработал, пользователь поправил её на странице, появился новый раунд),
изменение отклоняется с кодом `stale` и **ничего не перезаписывается**. `expected_version=-1` (по умолчанию)
означает «не проверять». `version` растёт на каждом сохранении задачи (`core/lazy/store.py`).

Проверка и запись — одна транзакция SQLite (`LazyStore.save_task(task, expected_version=...)`,
`BEGIN IMMEDIATE` + условный `UPDATE ... WHERE version = ?`): пишется только та версия, которую прочитали,
а не «последняя прочитанная этим объектом». Блокировка записи принадлежит файлу, поэтому compare-and-swap
держит и между процессами, а не только между потоками одного сервера. Просто «плюс один к версии при
сохранении» этого не даёт — две одновременные правки с одной версией обе прошли бы проверку, и вторая
молча потеряла бы первую. Поэтому из двух гонок проходит ровно одна, вторая получает `stale`.

## Проект

`project_id` — только проект **этого** пользователя: он проверяется в сервисе
(`web_chat/lazy/service.py`, `_checked_project`) против `space.project_store` его пространства. Через эту
проверку идут и инструменты, и API страницы (`POST /api/lazy/tasks`, `PATCH /api/lazy/tasks/{id}`,
`POST .../apply`), поэтому прямой HTTP-запрос с чужим или выдуманным `project_id` получает отказ,
а не задачу, привязанную к чужому проекту. Неизвестный проект → `project_not_found`; архивный →
`project_archived` (задача не создаётся и не меняется); пустая строка в `lazy_update` отвязывает задачу.
Проект наследуется следующим раундом серии, а чат шага заводится в проекте задачи
(`web_chat/lazy/runner.py`, `ensure_conversation`), с заметками проекта в начале.

Проект задачи — не просто ярлык: от него зависит, где шаг читает и пишет. Поэтому у этой границы два
правила.

1. **Пока задача работала, проект не меняется.** Чат шага создаётся в проекте задачи, и следующие шаги
   продолжают именно этот чат. Смена `project_id` у задачи, у которой уже есть рабочий чат
   (`Task.conversation_id` существует) или выполняется шаг, оставила бы сделанную работу в старом проекте,
   а задачу — с виду в новом. Такой `lazy_update` отклоняется с кодом `project_locked`; безопасный путь —
   завершить (или отменить) задачу и завести новую в нужном проекте. Если старый чат уже удалён, менять
   проект можно: следующий шаг заведёт чат заново, уже в новом проекте. Внутренний вызов без `space`
   (не может проверить, жив ли чат) считается «чат есть» и тоже получает отказ.
2. **Проект проверяется и в момент запуска шага.** Проект могли удалить или заархивировать после создания
   задачи. Удалённый проект в `UserSpace.chat_roots` даёт `project=None`, то есть шаг молча ушёл бы в личное
   пространство пользователя; архивный проект принял бы новую работу, хотя его работа не расширяется.
   `web_chat/lazy/runner.py` (`project_problem`) проверяет проект до создания чата: шаг не стартует вовсе
   (`StepOutcome("blocked")`), задача переходит в `paused` с причиной в истории, и в личное пространство
   ничего не попадает. Разблокировать — вернуть проект, разархивировать его или сменить проект у задачи
   (пока у неё нет рабочего чата) и снять паузу.

## Создание на паузе

«Подготовь, но не начинай» — один вызов, а не два: `lazy_create(..., status="paused")`.
Статус (`active` по умолчанию | `paused`) проверяется в `LazyAgents.draft` (`web_chat/lazy/service.py`)
вместе с остальными полями и ставится задаче **до** любого сохранения. Поэтому:

- в хранилище нет ни мгновения, когда такая задача `active`, — цикл сервиса, даже проснувшись от
  `wake()` сразу после сохранения, видит её уже на паузе;
- планировщик не делает паузную задачу eligible (`core/lazy/planner.py:279`: состояние `paused`,
  wait «Paused», шаг не размещается), поэтому ни `run_now`, ни тик сервиса не запускают её шаги,
  пока `lazy_update` не снимет паузу;
- `preview` понимает то же поле (`LazyChat._create_body`): паузная примерка честно показывает задачу
  без размещённого шага и не сохраняет ничего;
- неизвестный статус (`done`, `cancelled`, `draft`) — отказ `invalid` из `draft`, задача не создаётся
  (то же правило, что у `lazy_update`, `_edited`).

`create` + `update(status="paused")` этим свойством **не** обладает: сохранение будит цикл, и первый шаг
может стартовать в пределах тика между двумя вызовами. Такой путь не документируется и не поддерживается
как способ «подготовить».

## Запись чата шага

`Task.conversation_id` пишет `LazyAgents._remember_conversation`, когда раннер сообщает, в каком чате
работает шаг. Это единственное поле, которое сохраняет не пользователь, а ход задачи, поэтому запись —
compare-and-swap по только что прочитанной версии (`save_task(task, expected_version=...)`), а не
last-write-wins: иначе старая копия задачи, прочитанная до правки, вернула бы прежние `status`,
`project_id` и план. Если между чтением и записью задачу изменили, сохранение не проходит, задача
перечитывается и поле ставится на свежей версии (до трёх кругов).

Остаток, названный явно: если задача меняется быстрее, чем эти три круга успевают выиграть (пользователь
правит её без остановки), `conversation_id` в этот раз не записывается — в лог уходит предупреждение,
а следующий шаг задачи вызовет `_remember_conversation` снова (`ensure_conversation`), и ссылка на чат
появится тогда. Чужая правка при этом не теряется никогда.

## Безопасность и квоты

- Чей это пользователь, решает хост: клиент — `factory.lazy_agents`, который ставит пространство
  аутентифицированного пользователя (`web_chat/space.py`). Модель не передаёт `user_id`, путь, tenant,
  workspace и не может их подделать: таких полей в схемах нет.
- Автономные factory (`grid_mcp`, `agent_chat`, evals) пользователя не имеют: `lazy_agents=None`,
  все инструменты отвечают `unavailable` — идентичность не угадывается.
- Настройка задачи **не меняет глобальные квоты и доли** подписки: задача тратит подписку своего агента,
  а `cap` — недельный предел самой задачи (серии) сверх доли пула, по ledger за скользящие семь суток
  (`Task.cap`, `SERIES_WINDOW`). Не указан — предела нет; `0` — настоящий ноль. Размеры, приоритет,
  дедлайн и релиз — её собственные поля.
- Инструменты не создают чатов «на будущее»: чат появляется у шага, когда сервис его запускает.

## Ошибки

Ответ с ошибкой — JSON `{"error": "...", "code": "...", "isError": true}`. Коды:

| `code` | Когда |
|---|---|
| `invalid` | пустой заголовок, неизвестное поле, неверный дедлайн/версия, правка завершённой задачи |
| `stale` | `expected_version` не совпал: задачу изменили после чтения |
| `not_found` | задачи (или серии) нет у этого пользователя |
| `project_not_found` | проект не принадлежит пользователю |
| `project_archived` | проект архивный |
| `project_locked` | задача уже работала в чате своего проекта (или шаг выполняется): перенос в другой проект оставил бы работу позади |
| `unavailable` | в этой сессии нет пользователя/проектов |

## Активация

- Модуль `tools/lazy_tools.py` подхватывается реестром `tools/function_tools.py` автоматически
  (файл `*_tools.py` + словарь `LAZY_TOOLS`); `TOOL_EFFECTS` и `TOOL_ISOLATION` объявлены рядом.
- Агент получает инструменты только из конфигурации системы. В `examples/coder/config.yaml` объявлены все семь,
  `engineer` получает все семь, `general_purpose` — только читающие (`catalog`, `list`, `get`, `preview`).
- Работающий сервер и открытые сессии держат старые модули и конфиги: нужен перезапуск сервера и новый чат.

## Тесты

`tests/test_lazy_schedule.py` — расписание на модельных часах, без live-вызовов: интервал держит целый период,
поздний раунд пропускает слоты, `daily`/`weekly` в зоне пользователя, весенний разрыв и осенний откат DST,
пропущенный слот не догоняется, релиз держит план и `next_start >= scheduled_release`, будущий дедлайн работу
не держит, `cap` серии по ledger двух раундов, `cap=null` против `cap=0`, два раунда на симулированных часах,
`not_before`/`repeat` через инструменты и ISO-offset в DTO.

`tests/test_lazy_tools.py` — изоляция двух пользователей, проектный контекст и отказ на чужой/архивный проект,
повторный `create` с `request_id`, пауза/правка/отмена серии, `expected_version`, компактность DTO,
типизированные ошибки, отсутствие полей идентичности, автодискавери и активация в конфиге `coder`.
Отдельно проверены обходы: прямой вызов API страницы с чужим/выдуманным проектом (создание и правка),
две одновременные правки одной версии (проходит ровно одна), устаревшая правка после отработавшего шага,
неизвестные `size`/`priority`/`status` (отказ `invalid`, ничего не меняется), preview на пустом
хранилище (не остаётся ни задачи, ни настроек), отмена/пауза серии с идущим раундом (`_stops`),
чат следующего раунда — в проекте серии, создание сразу на паузе (в плане `paused`, ни один шаг не
eligible, неизвестный статус — `invalid` без задачи) и запись чата шага, которая не затирает
одновременную паузу/правку (CAS с перечитыванием).
