# Инструменты проектов для агентов

Агент организует проекты пользователя сам, без ручного копирования текстов в интерфейс.

| Инструмент | Что делает |
|---|---|
| `project_list` | список проектов (id, title, parent_id, description, archived, has_notes) |
| `project_get(project_id)` | один проект вместе с общими заметками |
| `project_ensure(title, parent_id="", description="")` | создаёт проект, только если под тем же родителем нет проекта с таким названием (без учёта регистра и лишних пробелов); иначе возвращает существующий (`created=false`) и ничего не перезаписывает |
| `project_add_notes(project_id, text, mode="if_empty")` | `if_empty`: пишет, только если заметки пусты (то же самое — no-op, другое — ошибка `conflict`); `append`: дописывает, если текста там ещё нет |

## Порядок работы

1. Сначала `project_list`; создавать только недостающее (`project_ensure`).
2. Контекст проекта — через `project_add_notes`; заметки подмешиваются в контекст чатов проекта.
3. Удаления среди инструментов нет намеренно.

## Безопасность

- Хранилище берётся из `factory.project_store`, который задаёт пространство (`web_chat.space`) аутентифицированного
  пользователя. Модель не передаёт `user_id`, путь или tenant; инструменты их не принимают.
- Защита от дублей — под блокировкой `ProjectStore` (повтор и гонка дают один проект). Иерархия и валидация — прежние
  (глубина до 3, цикл, длина названия/заметок).
- Создание проекта не запускает чатов, задач, напоминаний и фоновых работ.
- Ошибки типизированы (`code`): `title_required`, `parent_not_found`, `cycle`, `too_deep`, `not_found`, `conflict`,
  `invalid`, `unavailable`. Ответ несёт `isError: true`.

## Активация

Код подхватывается реестром `tools/function_tools.py` автоматически, но агент получает инструменты только из
конфигурации системы (`examples/coder/config.yaml`: `engineer` — все четыре, `general_purpose` — `list`/`get`).
Работающий сервер и уже открытые сессии держат старые модули и конфиги: нужен перезапуск сервера и новый чат.

## Источники factory и идентичность

- Веб-чат (`web_chat.space.UserSpace._build_factory`) — единственный путь, где `factory.project_store` задан: хранилище принадлежит пространству аутентифицированного пользователя. Провайдер модели (OpenCode, Claude Code CLI, API) на это не влияет: инструменты работают внутри того же factory.
- Автономные factory (`grid_mcp.build_supervisor`, `agent_chat`, `core/system_evaluation`) контекста пользователя не имеют: `project_store=None`, инструменты отвечают `unavailable`. user_id не угадывается и не принимается от модели. Штатной trusted runtime identity у MCP-сервера нет; её нужно вводить отдельным решением.
- Ошибка записи (OSError) -> `unavailable`; в лог пишутся только имя файла и тип ошибки, без пути и содержимого.

## Гарантии гонок

- Один процесс: `RLock` + атомарная запись (tmp + `os.replace`).
- Несколько процессов/объектов на одном файле: транзакция берёт `fcntl.flock` на `projects.json.lock` и перечитывает файл под замком, поэтому `ensure`/`add_notes` не теряют чужие записи и не дублируют. Без `fcntl` (не-POSIX) остаётся только внутрипроцессная гарантия.
- `ensure` для архивного проекта ничего не меняет: `status=archived` и подсказка, дубль не создаётся.
- `append` не дублирует только точный блок (разделение пустой строкой); подстрока дублем не считается.
