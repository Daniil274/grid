# Выпуск и безопасное обновление

Документ описывает, как выпускается подготовленная версия Grid и как её
безопасно включать. Он относится к выпуску **0.2.0** — основе ревизионной
безопасности (`core/revisions.py`), но не запускает его.

## Состояние 0.2.0: prepared, не active

- Код и документация версии 0.2.0 подготовлены в рабочем дереве.
- `releases/manifest.json` — машинная запись выпуска: `current = 0.2.0`,
  `status = prepared`. Она описывает **реализованное** поведение, а не планы.
- **Активация не выполнялась.** Ни перезапуск сервера, ни публикация образов, ни
  изменение рабочей конфигурации в рамках этой подготовки не производились.
- Включение версии — контролируемое действие пользователя: резервная копия →
  просмотр изменений → перезапуск → проверка. См. «Безопасное обновление».

## Критерии публикации

Выпуск можно публиковать (тег `v0.2.0`, пакет, образы), только если выполнено
всё перечисленное.

1. **Машинный манифест сходится с кодом.**

   ```bash
   python tools/release_check.py --json
   ```

   Код возврата 0, `ok: true`, `failed: []`. Проверяются: схема и версия
   манифеста, отсутствие секретов, уникальность версий, `current` — самая
   новая и равна `core.__version__`, дата, версии манифеста и контрактов, точные
   digest'ы четырёх контрактов, `permissions_authority = action_policy`,
   `legacy_conversations = read-only`, `repin = never`, отсутствие заявок на
   replay/exactly once, существование файлов перечисленных тестов.

   Аддитивный блок `context_reference_bootstrap` (описание reference-only
   bootstrap: действие, версия записи, эндпоинты, что не импортируется) —
   справочный: валидатор проверяет только перечисленные выше обязательные
   ключи, поэтому добавление блока не меняет ни один enforced-ключ
   совместимости и ни один digest контракта.

2. **Тесты ревизий и reference-only bootstrap проходят.**

   ```bash
   pytest -q tests/test_revision_compatibility.py
   pytest -q tests/test_context_migration.py
   node --test tests/web_chat_reference.test.mjs
   ```

   Плюс полный набор проекта в чистом окружении (см. `.github/workflows/ci.yml`):
   `pytest -o addopts="" -ra --strict-markers --timeout=300`, ruff только по
   ошибкам (`E9,F63,F7,F82`), тесты интерфейса Node, сборка образов.

3. **Заметки о выпуске описывают реализацию.** Никаких «будет», «планируется»
   или заявок на replay/exactly once: см. `CHANGELOG.md` и
   `docs/revisions.md`.

4. **Независимая проверка в чистом checkout.** Не в рабочем каталоге с боевыми
   данными и не с боевым `.env`:

   ```bash
   git clone <repo> /tmp/grid-release-check
   cd /tmp/grid-release-check
   test ! -e .env                 # боевого .env здесь быть не должно
   test ! -e config.yaml          # боевой конфигурации тоже
   git status --short             # пусто: рабочее дерево чистое
   python -m venv .venv && . .venv/bin/activate
   python -m pip install -e ".[dev]"
   python tools/release_check.py --json
   pytest -q tests/test_revision_compatibility.py
   pytest -q tests/test_context_migration.py
   ```

   В CI этот же смысл закреплён отдельной задачей `release`: шаг проверяет, что
   в checkout нет `.env`, валидатор запускается **до** установки зависимостей
   (он офлайн), затем идут фокусные тесты. Ветка/тег без манифеста или с
   расходящимся манифестом не публикуется: CD вызывает CI и дополнительно
   сверяет тег с `current`.

5. **Старые небезопасные сборки не остаются навсегда.** После проверки новой
   версии прежние образы и бинарники выводятся из эксплуатации в объявленное
   окно; держать старую сборку, не проходящую ревизионные проверки, бессрочно
   нельзя. Откат — временная мера на время окна, а не постоянная конфигурация.

6. **Никаких обходов.** Нельзя «починить» публикацию правкой
   `releases/manifest.json`, подменой digest, копированием манифеста между
   диалогами или отключением проверки. Расхождение — это сигнал, а не
   препятствие.

## Безопасное обновление (активация)

Активация выполняется пользователем и только после резервной копии и просмотра.

1. **Остановите запись.** Дайте текущим запросам завершиться штатно (см.
   [server-restart.md](server-restart.md)); не обрывайте процесс посреди шага.
2. **Сделайте резервную копию** до запуска новой версии:
   - каталог диалогов `<data>/conversations/` (или `conversations.json`);
   - `GRID_SECRETS_KEY` — отдельно от копии данных: без ключа зашифрованные
     диалоги не читаются;
   - `config.yaml`, файлы skills, локальные tool-пакеты;
   - action policy и её файл;
   - `.env` (секреты) — в защищённое место, не в репозиторий.
3. **Просмотрите изменения** между прежней и новой версией: `CHANGELOG.md`,
   `docs/revisions.md`, diff конфигурации. Оцените, какие диалоги перестанут
   продолжаться.
4. **Перезапустите под своим контролем** — вручную или штатным управляемым
   перезапуском. Автоматической активации нет.
5. **Проверьте после старта:** сервер поднялся, старые диалоги открываются для
   чтения, новый диалог закрепляется и продолжается, отказов с неожиданным
   `code` нет, журналы не содержат секретов.

Перед активацией полезно помнить: после неё **все сохранённые диалоги без
манифеста становятся legacy** — читаемыми, но непродолжаемыми.
Автоматической миграции истории нет. Явный путь вперёд — reference-only
bootstrap: новый **пустой** диалог, закреплённый за этим окружением, со ссылкой
на старый как на справочные данные (см. [revisions.md](revisions.md)).
Ничего исполняемого он не переносит, исходный диалог не переписывает, не
перезакрепляет и не удаляет. Новые диалоги закрепляются автоматически при
первом ходе.

**Права после bootstrap обычные.** Новый диалог действует под текущую
конфигурацию и action policy; reference-запись не выдаёт и не расширяет
полномочия. Старая история не попадает в контекст агента автоматически — её
может прочитать и скопировать только человек по ссылке на источник.

## Откат

Откат — это откат **кода**, а не откат мира:

- **Код** можно вернуть на предыдущую версию и запустить её с резервной копией
  данных. 0.2.0 не выполняет миграций хранилища и не переписывает старые
  диалоги; она лишь добавляет манифест диалогам, закреплённым после обновления.
- **Внешние операции не откатываются вслепую.** Инструменты могли уже сделать
  push, деплой, отправку сообщения, изменение во внешнем сервисе. Такие
  действия разбираются отдельно; автоматического «отката» у них нет.
- **Данные и схемы не откатываются вслепую.** Не удаляйте и не переписывайте
  каталог диалогов, манифесты и данные внешних систем, чтобы «совместить»
  версии. Сначала сохраните копию, затем проверьте поведение прежней версии на
  копии.

  Reference-only bootstrap хранилище не переписывает: он **добавляет** новый
  пустой диалог, его закрепление и запись `migration` в metadata цели. Старые
  диалоги остаются байт-в-байт прежними, поэтому такие добавления можно
  оставить на месте при откате кода; удалять их нужно осознанно, как обычные
  чаты.
- **Проверьте откат теми же средствами:** `python tools/release_check.py
  --json` и фокусные тесты на возвращённом коде; версия в манифесте должна
  соответствовать возвращённому коду, иначе валидатор честно скажет, что
  манифест описывает другой выпуск.
- После окна отката старую сборку выводят из эксплуатации; постоянное
  сосуществование версий с разными контрактами не поддерживается.

## Что именно проверяет CI

- `lint` — ruff, только ошибки, способные сломать выполнение.
- `test` — pytest на Python 3.11 и 3.12 (включая `tests/test_revision_compatibility.py`
  и `tests/test_context_migration.py`).
- `release` — офлайн-валидатор `tools/release_check.py --json` до установки
  зависимостей, проверка отсутствия `.env` в checkout, фокусные тесты ревизий.
- `js` — тесты интерфейса, включая `tests/web_chat_reference.test.mjs`
  (предпросмотр, согласие владельца, POST с токеном, баннер цели).
- `images` — сборка обоих образов и проверка инструментов песочницы.

CD вызывает CI целиком, поэтому опубликовать непроверенную сборку нельзя.
