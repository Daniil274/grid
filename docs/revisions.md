# Ревизии диалогов: закрепление, совместимость и отказы

Начиная с Grid **0.2.0** сохранённый диалог нельзя продолжить в произвольном
окружении: при первом ходе, который в него пишет, диалог **закрепляется** за
неизменяемым манифестом ревизии, а каждый следующий ход сначала проверяет этот
манифест и только потом делает внешние операции (вызов модели, инструмент,
подагент). Реализация — `core/revisions.py`; проверка встроена перед
маршрутизацией и прогревом в `core/factory/turns.py` и общая для веб-чата,
ленивых агентов и CLI.

Версия кода в этой поставке — **0.2.0** (`core/__init__.py`), запись о выпуске —
`releases/manifest.json`. Выпуск **подготовлен, но не активирован**: эта
документация не запускает обновление. Решение о перезапуске и активации
принимает пользователь (см. [release-process.md](release-process.md)).

## Когда диалог закрепляется

- **Новый диалог** — при первом ходе, который в него пишет. Манифест строится
  из окружения *этого* хода, сохраняется строго и читается обратно; дальнейшие
  ходы судят по сохранённому манифесту, а не по копии в памяти.
- **Пустой сохранённый диалог не закрепляется.** «Новый» здесь значит «создан
  в этом процессе» (`is_new_context`), а не «пустой»: пустой диалог,
  прочитанный из хранилища после перезапуска, — такой же *legacy*, как и
  непустой. Отсутствие манифеста — часть того, что было сохранено, поэтому
  пустой сохранённый диалог читается, но задним числом не принимается и не
  закрепляется (`core/context.py`, `pin_revision`). Явный путь вперёд —
  reference-only bootstrap: он создаёт **новый** диалог, а не закрепляет
  старый.
- **Сохранённый диалог без манифеста** — *legacy*. Он читается, но продолжить
  его нельзя и закрепить задним числом тоже (см. ниже).
- **Ветка (branch) диалога** наследует тот же манифест с тем же окружением,
  переименованным под новый контекст. Это копия ревизии, а не повторное
  закрепление.
- Неразрешённая конфигурация системы никогда не попадает в манифест: сначала
  проверяется окружение, потом пишется закрепление.

## Контракты

Совместимость разделена на четыре независимо версионируемых контракта — у них
разные вопросы совместимости:

| Контракт | Имя | Версия | Что описывает |
|---|---|---|---|
| history | `grid.context.history` | 1 | поля `conversation_history`, `execution_history`, `metadata`, `created_at`, `updated_at` |
| checkpoint | `grid.context.checkpoint` | 1 | снимок рабочего каталога перед ходом; возобновляет только файлы workspace |
| runtime | `grid.agent.runtime` | 1 | сериализация истории — JSON |
| tools | `grid.tools.contract` | 1 | семантика сохранённых вызовов; полномочия — у action policy |

Версия каждого контракта и digest его определения входят в манифест. Манифест
версии 1 поддерживается; манифест другой версии **отвергается, а не
угадывается**.

## Совместимость: точное равенство, консервативно

Манифест считается совместимым, только если совпадает всё перечисленное:

- **Grid** — точное равенство версии (`grid_version`). Смена версии Grid
  делает закреплённый диалог непродолжаемым.
- **Manifest version** — только поддерживаемые; иначе отказ.
- **Contract version и digest** — поддерживаемая версия и **точный** digest
  определения. Изменение определения контракта без смены версии — отказ.
- **Python** — точная minor-серия (`3.12`, а не `3.11`).
- **Конфигурация системы** — точный digest разрешённой конфигурации.
- **Проекция** (`defaults`) — только для чтения людьми и агентами; по ней
  ничего не решается.

Это намеренно консервативно: ложный отказ дешевле, чем продолжение диалога,
записанного при других промптах, инструментах, лимитах или версии кода.

## Что вызывает отказ

Digest конфигурации покрывает **разрешённую** конфигурацию целиком, включая
промпты, а также внешние источники, на которые она ссылается: файлы инструкций
системных skills и исходники локальных tool-пакетов (`tool_package`, при
включённых `project_tools`). Поэтому отказом заканчивается не только правка
`config.yaml`, но и:

- изменение промпта, модели, лимитов, набора или типа инструментов агента;
- правка `.md`/`.txt` файла skill, на который ссылается агент;
- правка исходников локального tool-пакета.

Продолжение диалога в **другой системе** (другой пользователь, другой каталог
конфигурации, другой набор агентов) тоже, как правило, заканчивается отказом:
её разрешённая конфигурация даёт другой digest. Совпадающая проекция этому не
помогает.

Машиночитаемые причины — поле `code` в `ContextCompatibilityError` и в ответах
`core.revisions`:

| Код | Значение |
|---|---|
| `revision.compatible` | ревизия цела и совместима |
| `revision.legacy_context` | диалог сохранён до появления ревизий: только чтение |
| `revision.manifest_tampered` | манифест изменён после закрепления |
| `revision.manifest_version_unsupported` | неизвестная версия манифеста |
| `revision.grid_version_changed` | диалог закреплён другой версией Grid |
| `revision.contract_version_unsupported` | неизвестная версия контракта |
| `revision.contract_changed` | определение контракта изменилось при той же версии |
| `revision.runtime_changed` | другая minor-серия Python |
| `revision.system_config_changed` | изменилась разрешённая конфигурация системы |
| `revision.system_unresolved` | у хода нет разрешённой конфигурации для закрепления/проверки |
| `revision.manifest_malformed` | манифест не той формы |
| `revision.manifest_immutable` | зарезервированный код повторного закрепления: `pin_revision` возвращает `False`, существующий манифест не заменяется |
| `revision.context_mismatch` | манифест принадлежит другому диалогу |
| `revision.context_unknown` | диалог неизвестен этому процессу или у менеджера нет ревизий |

Неизвестный диалог и менеджер контекста без API ревизий **отказывают**, а не
разрешают ход. Единственное явное исключение — `revision_trusted_ephemeral =
True` у вызывающего, который вообще не хранит диалоги; это не общий fallback.

## Legacy и reference-only bootstrap

Диалог без манифеста — **legacy**: его историю можно читать, но продолжать
нельзя. Закрепить его при загрузке или при первом ходе нельзя: иначе
непроверенная история молча получила бы ревизию. То же относится к диалогу,
закреплённому за другой версией Grid, другим runtime или другой разрешённой
конфигурацией: его ревизия цела, но исполнять её историю здесь нельзя.

Для таких диалогов есть один поддерживаемый путь вперёд — **reference-only
bootstrap** (`core/migration.py`). Это не миграция истории и не её продолжение:

- создаётся **новый пустой диалог**, закреплённый за окружением этого
  сервера. Его история пуста: первый ход в нём — новый ход, а не продолжение;
- исходный диалог **не переписывается, не перезакрепляется, не редактируется и
  не удаляется**. Его история и артефакты остаются там, где были; новый диалог
  хранит только *ссылку* на них и их digest'ы;
- **ничего исполняемого не импортируется**: ни сообщения и ответы, ни
  executions, ни SDK-сессии агентов, ни очередь сообщений, ни pending-run, ни
  checkpoints, ни файлы workspace, ни approvals, ни credentials, ни action
  policy. Отчёт называет их и их количество, но не переносит;
- provenance источника не приукрашивается: у legacy-диалога без манифеста он
  **неизвестен** (`provenance: "unknown"`) — история пришла из runtime, чьи
  контракты не записаны, — а у диалога с целым, но несовместимым манифестом
  записан как `pinned` с версией Grid и digest'ом его ревизии. В обоих случаях
  это только справочные данные, а не исполняемое состояние;
- **исторические данные не становятся доступны агенту автоматически.** Ни
  чат, ни модель, ни инструменты не получают старую историю в контекст: она
  доступна человеку по ссылке на исходный диалог, и только то, что он сам
  скопирует и вставит в новое сообщение, попадает в новый запрос.

Права при этом не меняются: целевой диалог получает **обычные текущие
полномочия** — те, что дают его конфигурация и action policy. Reference-запись
ничего не разрешает и не расширяет; подтверждение миграции — это привязка к
состоянию источника, а не capability.

### Как это устроено

Действие машиночитаемо и версионировано: `action = "context.reference_bootstrap"`,
`version = 1`. Запись хранится в metadata целевого диалога под ключом
`migration`.

1. **Сухой прогон (dry run)** — пишет **ничего**. Возвращает отчёт
   (`status`, `code`, `reason`, `source`, `target`, `reference`,
   `confirmation`) и токен подтверждения, привязанный к точному состоянию
   источника: его содержимому, манифесту ревизии и metadata (кроме
   изменчивых `title`, `active_branch`, `last_context_assembly`), а также к
   самому действию, явно выбранным `system_key`/`agent_key` цели и digest её
   целевого окружения (`target.environment_digest`). Смена конфигурации после
   предпросмотра тоже делает подтверждение устаревшим.
2. **Подтверждение владельцем** — в интерфейсе это отдельная галочка согласия
   в диалоге «Reference-only copy…»; в API — `confirm: true` **и** токен из
   сухого прогона. Без обоих изменяющий вызов отвергается
   (`migration.confirmation_required`).
3. **Применение** — план пересчитывается заново под процесс-локом; если
   источник изменился после предпросмотра, токен не подходит
   (`migration.confirmation_stale`) и **ничего не создаётся**. При успехе
   сначала строго сохраняется закрепление нового диалога, затем — запись
   `migration`; если закрепление не удалось, пустой диалог удаляется, чтобы не
   осталось полумигрированной цели.
4. **Идемпотентность** — повторное применение того же запроса в том же
   окружении не создаёт второй диалог: возвращается `migration.completed` с уже
   существующей целью (`idempotent: true`), даже если в цели уже есть ходы.

Поддерживаемые команды (`web_chat/server.py`):

| Метод и путь | Что делает |
|---|---|
| `GET /api/chat/conversations/{id}/migration` | сухой прогон: отчёт и токен; ничего не пишет |
| `POST /api/chat/conversations/{id}/migration` | создаёт пустой reference-only диалог; тело — `{"plan_token": "<токен из GET>", "confirm": true}` |

Схема тела — `web_chat.schemas.MigrationRequest`: `plan_token` (строка 16…128
символов) и `confirm` (bool, по умолчанию `false`). Ответ — тот же отчёт, что у
сухого прогона. Статусы ответа: `200` для `applied`/`completed`, `409` для
отказов и устаревшего/отсутствующего подтверждения, `503` при
`migration.system_unresolved`, `404` для неизвестного диалога, `400` без
`confirm`.

В интерфейсе точка входа — пункт «Reference-only copy…» в меню диалога в
рейле; он открывает диалог предпросмотра (`web_chat/js/ui/migration-dialog.js`)
и после создания открывает новую пустую беседу. В ней постоянно висит
баннер-ссылка на источник (`web_chat/js/ui/reference-banner.js`): он говорит,
что история не импортирована, не воспроизводится и файлы не восстанавливаются,
и предлагает открыть старый диалог в новой вкладке, скопировать нужное и
вставить в новое сообщение.

### Отказы, которые остаются

- **Строгий точный gate никуда не делся.** Продолжение диалога по-прежнему
  требует точного равенства версии Grid, поддерживаемых версий манифеста и
  контрактов, точных digest'ов определений, minor-серии Python и digest'а
  разрешённой конфигурации. Reference-only bootstrap не ослабляет ни одну из
  этих проверок: он даёт *ссылку*, а не совместимость.
- **Повторного закрепления (repin) нет.** Ни исходный диалог, ни цель не
  перезакрепляются: манифест неизменяем, запись с манифестом другой формы или
  чужого диалога отвергается.
- **Malformed, tampered и future отвергаются.** Манифест не той формы
  (`migration.source_malformed`), изменённый после закрепления
  (`migration.source_tampered`), из более новой версии формата
  (`migration.source_future`) или с неизвестным вердиктом целостности
  (`migration.source_integrity_unknown`) не используется даже как источник
  ссылки. Fail-closed: неизвестный код целостности никогда не читается как
  «просто несовместимый».
- **Совместимый источник не копируется**: ему не нужна ссылка, его можно
  продолжать (`migration.source_compatible`). Пустой и незакреплённый источник
  тоже не мигрируются (`migration.source_empty`, `migration.source_unpinned`).
- **Цель, закреплённая за изменившейся конфигурацией, не перезакрепляется.**
  Если существующая reference-only цель больше не разрешается в этом
  окружении, отчёт — `migration.target_incompatible` с безопасным следующим
  шагом: запустить reference-only bootstrap **из самой цели**, чтобы перенести
  ссылку дальше. Ничего не создаётся и не переписывается.
- Отказ не оставляет следа хода: история, executions, журнал и pending-запись не
  меняются.

## Полномочия

Манифест **не** является разрешением. Действия каждого хода — и закреплённого,
и нового — решает action policy (`ACTION_POLICY.md`). Закрепление фиксирует
совместимость истории и среды, но не расширяет и не сужает права, выданные
конфигурацией и политикой.

## Секреты и приватность

В манифест никогда не попадают:

- тексты промптов;
- credentials (API-ключи, токены, пароли), значения переменных окружения;
- абсолютные пути каталогов.

Хранится только проекция: ключи агентов, моделей и инструментов, провайдеры,
размеры контекста и разрешённые лимиты (`max_turns`, `timeout`,
`max_history`), режим и имя файла action policy. Digest считается по
редактированному материалу: поля с именами вроде `api_key`, `token`, `secret`,
`password`, `authorization`, `headers` заменяются на `<redacted>`, а
значения, похожие на живые ключи, не хешируются. Файлы, чьё имя похоже на
хранилище секретов (`.env`, `*.pem`, `*.key`, `id_rsa`, …), для digest не
читаются вовсе: проверяются только файлы исходных расширений (`.py`, `.md`,
`.txt`, `.yaml`, `.yml`, `.toml`, `.json`, `.cfg`, `.ini`, `.sh`), и их
содержимое хешируется целиком (sha256 блоками по 64 КиБ), без «учёта по
размеру» — размер не подменяет содержимое.

Для reference-only bootstrap хешируется только материал источника, и хеш
редактируется так же: в отчёт и в запись цели попадают digest'ы и счётчики, но
не тексты сообщений, ответов, использования инструментов, очередей или сессий.
Ни один секрет не переезжает в цель: она создаётся пустой.

Ротация ключа не делает диалог непродолжаемым; изменение промпта — делает.

## Границы гарантии

Манифест описывает совместимость **сохранённого диалога**. Он не даёт и не
обещает:

- повторного воспроизведения (replay) хода;
- гарантии «ровно один раз» (exactly once) для внешних операций;
- восстановления состояния Python-процесса, незавершённого сетевого запроса или
  каждого токена потока.

Обрыв между внешним действием и записью результата по-прежнему оставляет
неизвестный исход; такие вызовы не повторяются автоматически (см.
[server-restart.md](server-restart.md)).

## Что делать при отказе

1. Прочитайте `code` и текст ошибки: в них указано, что именно разошлось.
2. Если нужна прежняя история — откройте её для чтения и начните новый диалог.
   Для legacy-диалога или диалога из другого окружения используйте
   reference-only copy (см. выше): он создаст новый пустой диалог со ссылкой на
   старый.
3. Не редактируйте манифест и не копируйте его между диалогами: изменённый
   манифест отвергается (`revision.manifest_tampered`).
4. Если отказ вызван изменением конфигурации, верните прежнюю конфигурацию и
   перезапустите сервер — закреплённые диалоги снова станут совместимыми.
5. Для агентов: не пытайтесь обойти отказ другим инструментом или агентом;
   отказ означает, что продолжать эту историю в этом окружении нельзя.

## Проверка

```bash
python tools/release_check.py --json
pytest -q tests/test_revision_compatibility.py
pytest -q tests/test_context_migration.py
node --test tests/web_chat_reference.test.mjs
```

`release_check.py` работает офлайн, не пишет файлов и сверяет
`releases/manifest.json` с определениями контрактов в `core/revisions.py` и
версией кода. Ненулевой код возврата — манифест не описывает этот код.

`tests/test_context_migration.py` покрывает сухой прогон и его «ничего не
пишет», привязку токена к точному состоянию источника, обязательное
подтверждение и устаревший токен, создание одной пустой закреплённой цели при
сохранённом оригинале, отсутствие переноса approvals/очередей/сессий/
credentials, идемпотентность, отказы tampered/future/malformed/foreign,
`target_incompatible` без перезакрепления и API-границы
(`web_chat/server.py`). `tests/web_chat_reference.test.mjs` покрывает
пользовательский путь: предпросмотр, галочку согласия, POST с токеном, баннер
и пункт меню в рейле.
