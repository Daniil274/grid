# Режимы доступа, выкладка и границы изоляции

Сервер web-чата умеет работать в двух режимах, и выбрать один из них нужно
явно: без `--accounts` или `--unsafe-single-user` он не стартует. Это сделано
намеренно — «один пользователь без входа» не должен получаться случайно из
голой команды `grid-web-chat`.

| Режим | Флаг | Кто пользователь | Где уместен |
|---|---|---|---|
| Сайт для нескольких пользователей | `--accounts` | Вошедший человек; у каждого своё пространство | Хост или VM с Docker, за HTTPS-прокси |
| Один локальный пользователь | `--unsafe-single-user` | Каждое соединение — один и тот же админ, без проверки | Машина, к которой нет чужого доступа |

## Образ: безопасный режим по умолчанию

`Dockerfile` стартует сервер с `--accounts --data-dir /data` (без `--path`).
Это значит:

* на каждом соединении обязателен вход: `docker run -p 8000:8000` больше не
  отдаёт рабочую папку, ключи и агентов первому, кто дотянется до порта, —
  неявного админа нет;
* состояние сервера (база аккаунтов и каталоги пользователей) живёт в `/data`:
  каталог создан при сборке с владельцем `grid` (uid 1000), а том или каталог
  хоста поверх него должен быть этому uid доступен на запись; первый
  администратор заводится командой `grid-web-chat accounts create-admin`;
* агенты каждого пользователя работают в его контейнере, поэтому серверу нужен
  Docker backend. Если демон недоступен, сервер **не стартует** (fail closed) и
  пишет причину — вместо запуска команд на этой машине;
* образ **не подключает Docker socket сам** и не делает это неявно. Доступ к
  демону выдаёт оператор: `-v /var/run/docker.sock:/var/run/docker.sock`
  (эквивалент root на хосте, см. ниже), отдельный демон (dind) или
  `--trusted-users` для полностью доверенных пользователей;
* `-p 127.0.0.1:8000:8000` публикует порт только на этой машине; с аккаунтами
  публикация шире допустима (вход обязателен), но перед сервером всё равно
  нужен HTTPS-прокси, иначе пароль и cookie идут открытым текстом.

Локальный режим без входа так по умолчанию не включается никогда: его выбирают
явно, переопределив команду образа на `--unsafe-single-user` (пример в README,
«Запуск в контейнере»), и публикуют порт только на loopback.

## `--accounts`: сайт со входом

Запуск — `deploy/grid-web-chat.service` (systemd) и `deploy/Caddyfile`
(HTTPS-терминация). Юнит слушает `127.0.0.1:8000`, Caddy проксирует на него
`chat.example.com`; uvicorn доверяет прокси на той же машине по умолчанию,
поэтому реальный адрес клиента доходит до ограничения попыток входа, а cookie
получает `Secure`.

Сервер отвечает только на известные ему имена Host: loopback-имена, адрес
`--host`, значения `--trusted-host` и публичные имена из `--allowed-origin`.
Caddy пересылает Host `chat.example.com`, поэтому в поставляемом юните есть
`--allowed-origin https://chat.example.com` — ровно тот адрес, который
обслуживает поставляемый Caddyfile. При смене домена меняйте оба файла вместе:
имя, которое Caddy пересылает, а юнит не перечисляет, получает 400 до страницы,
входа и websocket. Прокси на другой машине перечислите в
`--forwarded-allow-ips`.

В режиме `--accounts` агенты каждого пользователя работают в его контейнере,
независимо от `isolation.enabled` в конфиге. Запуск контейнеров требует Docker
на хосте; участие пользователя `grid` в группе `docker` эквивалентно root на
этой машине. Поэтому сервер выкладывают на отдельный хост или VM, а не на
машину с чужими задачами.

Данные сервера — каталог `--data-dir` целиком: база аккаунтов и каталоги
пользователей. База аккаунтов — SQLite в режиме WAL; копируйте её при
остановленном сервере или через `sqlite3 accounts.db ".backup copy.db"`.

## `--unsafe-single-user`: явный локальный режим

Так запускаются оба сервиса `docker-compose.yml` — это явный opt-in локального
режима, а не поведение образа по умолчанию, — и команда `docker run` из README,
переопределяющая стандартную команду образа. Это по-прежнему сервер без входа:
любой, кто дотянется до порта, действует как локальный админ — с его рабочей
папкой, ключами и агентами. Поэтому:

* compose публикует порт только на `127.0.0.1`; с удалённой машины заходите
  через SSH-туннель;
* `docker run -p 8000:8000` открывает порт на всех интерфейсах — для сервера
  без входа используйте `-p 127.0.0.1:8000:8000` или не переопределяйте
  команду образа и работайте на `--accounts`;
* не ставьте перед этим режимом публичный прокси: HTTPS не добавляет
  аутентификацию.

## Сеть контейнеров: что изолировано и что нет

Каждый пользователь получает свою bridge-сеть (метка `grid.network.tenant`),
контейнеры пользователя подключены только к ней; container-to-container трафик
на этой сети выключен (`enable_icc=false`). Контейнер, запущенный старым Grid
на `network_mode="host"`, при следующем обращении пересоздаётся на сети
пользователя. Это устраняет общую сеть контейнеров; фактическую межсетевую
изоляцию необходимо проверить на используемом Docker и firewall.

Это **не полная сетевая песочница** и не граница «контейнер ↔ хост»:

* шлюз Docker (адрес хоста со стороны bridge) достижим; всё, что на хосте
  слушает `0.0.0.0` или опубликовано через `-p`, достижимо с контейнера;
* link-local `169.254.169.254` (cloud metadata) на хосте с таким сервисом тоже
  достижим;
* публикация портов контейнера — вопрос firewall, а не этой сети; модуль сам
  портов не публикует и не может запретить Docker публиковать их.

Закрыть эти маршруты можно только на хосте: firewall-правилами для bridge-сети
или `internal`-сетью с явным egress-прокси как единственным выходом. Без такой
инфраструктуры сеть изолирует пользователей друг от друга, но не от хоста.
DNS и исходящий NAT в интернет (модельные провайдеры) при этом сохраняются.

### Прокси и loopback

Сервер передаёт контейнеру переменные `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`
и их строчные варианты. Если прокси задан через loopback (`127.0.0.1`,
`localhost`), для контейнера он переписывается на `host.docker.internal`
(на Linux — запись `host-gateway` в hosts контейнера). Это лишь меняет имя в
URL: прокси, слушающий **только** loopback хоста, через адрес шлюза
недостижим. Чтобы схема работала, прокси должен слушать адрес шлюза Docker или
`0.0.0.0`; иначе оставьте прокси вне контейнерной схемы либо не используйте
его для контейнеров. `NO_PROXY` — список имён, а не адрес подключения, и
передаётся без изменений.

## Остальные ограничения

* `grid-control serve` (профиль `evolution`) слушает plain HTTP, токен идёт в
  заголовке `Authorization`. Пока он на `127.0.0.1` — это приемлемо; при
  передаче через недоверенную сеть его может получить участник с доступом к
  сетевому пути. Само соседство в Docker-сети не доказывает перехват.
  Для выкладки используйте TLS или защищённый локальный транспорт.
* `/node/pair` защищён одноразовым кодом с TTL, но без отдельного rate limit;
  `/node/connect` требует bearer-токен устройства.
* `.env` попадает в контейнер сервера целиком (`env_file`), а агенты выполняют
  команды — не держите в нём ключи, которые не нужны этому серверу.
* Политика действий (`ACTION_POLICY.md`) дополняет изоляцию, но не заменяет
  firewall, права файлов и контроль внешних сервисов.

Аудит, из которого выросли эти ограничения, —
`grid-security-audit-2026-11-06.md` в пространстве проекта.

## Отзыв сессии у открытых соединений

Accounts-сервер повторно проверяет сессию перед каждой командой chat WebSocket
и каждым вводом в live-view устройства. Выход, отключение аккаунта, отзыв при
смене роли/пароля и истечение сессии запрещают новые команды, включая одобрение
действий. Idle-соединения проверяются раз в 30 секунд и закрываются с кодом
1008; при ошибке проверки полномочий соединение тоже закрывается. Это не
гарантия мгновенного прекращения уже отправляемых кадров или ответов.

Уже запущенный агентный ход автоматически **не отменяется**: он дорабатывает
и сохраняет результат. Уже авторизованная HTTP-выдача файла также не обрывается
посреди ответа. Отключение аккаунта пока не является командой немедленной
остановки всех его фоновых задач.
