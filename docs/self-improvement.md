# Контроллер самоулучшения

Grid изменяет себя через эксперименты. Администратор готовит коммит, а отдельный
контроллер сравнивает его с исходной версией. Рабочая система продолжает работать.
Контроллер не импортирует код кандидата и не использует старый `core/improvement`.

## Границы ответственности

* Администратор: задача, гипотеза, изменения кода и конфигураций, разбор отчёта.
* Контроллер: точные версии, ресурсы Docker, журнал, запуск и решение.
* Проверяющий: внешние задания и объективные условия результата.
* Менеджер развёртывания: переключение сессий и восстановление данных.

Администратор должен работать в контейнере с отдельной копией репозитория.
Контроллер устанавливается отдельно на хосте. Его файлы, политика, журнал и
Docker socket не монтируются в администратора или кандидата. Разные Python-модули
в одном доступном агенту окружении сами по себе не обеспечивают эту границу.

## Первый реализованный контракт

`grid-control evaluate` принимает репозиторий, два Git ref и политику оператора.
Ref сразу преобразуются в SHA коммитов, образы — в локальные immutable image ID.
Используются только закоммиченные файлы; рабочее дерево и его `.env` не копируются.

Контроллер собирает два образа из одного установленного runtime. Своим Dockerfile
он помещает исходники в `/opt/grid/candidate` и запускает `python -m web_chat` с
`routing.yaml` именно этой версии. Dockerfile кандидата не исполняется. У runtime
уже должны быть все Python-пакеты и внешние инструменты. Изменение зависимостей
требует нового runtime от оператора и повторного сравнения обеих версий на нём.

Каждый прогон получает отдельную сеть и пустой workspace. Нет host mounts,
привилегий, Docker socket и опубликованных портов. Ограничены память, CPU,
количество процессов и размер временных файлов. Корневая файловая система
доступна только для чтения. Сеть по умолчанию не имеет внешнего доступа.

Проверяющий запускается в отдельном образе Python. Он получает только адрес
кандидата и проверки; не получает его исходники и ключи провайдеров. HTTP redirects
запрещены, размер JSON ограничен. Поддерживаются HTTP status и точное сравнение
значения по JSON Pointer. Это проверки совместимости API, а не доказательство
качества ответа агента или устойчивости к намеренно вредоносному коду.

Текущий набор проверок выполняется несколько раз для обеих версий с чередованием
порядка. Кандидат принимается, только если все проверки проходят во всех прогонах
и достигнут `min_improvement`. Нулевой порог означает отсутствие регрессий;
положительный требует увеличения доли успешных проверок.

Решение, политика и её SHA-256, версии, образы и каждый прогон записываются в
SQLite. Ошибка инфраструктуры или очистки означает `failed`, а не `accepted`.
При аварийном завершении ОС освобождает блокировку эксперимента; оставшиеся
ресурсы можно очистить командой `cleanup`. Она откажется трогать активный запуск.
Образы сохраняются для повторной проверки; контейнеры и сети удаляются.

## Использование

Сначала соберите полный runtime Grid и загрузите образ Python для проверяющего.
Политику храните вне доступной администратору рабочей директории:

```json
{
  "runtime_image": "grid-agent-system:local",
  "verifier_image": "python:3.11-slim",
  "repetitions": 3,
  "timeout_seconds": 180,
  "min_improvement": 0.0,
  "checks": [
    {"name": "web", "path": "/"},
    {"name": "autoroute", "path": "/api/chat/bootstrap", "json_pointer": "/routing_enabled", "expected": true},
    {"name": "catalog", "path": "/api/chat/bootstrap", "json_pointer": "/multi_system", "expected": true}
  ]
}
```

```bash
grid-control evaluate --repo /repo/grid --baseline BASE_SHA --candidate CANDIDATE_SHA --policy /control/policy.json
grid-control show EXPERIMENT_ID
grid-control cleanup EXPERIMENT_ID
```

Для испытаний с внешним провайдером оператор явно включает `allow_network` и
задаёт `environment_names`, например `["OPENROUTER_API_KEY"]`. Значения берутся
из окружения контроллера, передаются только процессу кандидата и не записываются
в отчёт. Docker-оператор по-прежнему может видеть окружение контейнера.

## Мастерская и репозиторий эволюции

Grid эволюционирует на ветке `stable` голого репозитория, в который пишет только
контроллер (`grid-control init --repo <evolution.git> --from <checkout>`).
Администратор (`examples/system-admin`) работает в контейнере-мастерской
(`docker compose --profile evolution up workshop`) со своим клоном `stable`,
полученным через `GET /source` в виде git bundle.

* `control_begin` сбрасывает мастерскую на текущий `stable` и запоминает baseline.
* `control_submit` коммитит изменения и отправляет `POST /experiments` с bundle,
  в котором лежат только новые коммиты. Контроллер проверяет, что кандидат
  продолжает baseline, и кладёт его в `refs/candidates/<sha>`. `stable` при этом
  не меняется.
* `grid-control promote <id>` — подтверждение оператора: переносит `stable` на
  принятого кандидата сравнением-с-заменой и отказывает, если `stable` сдвинулся
  после baseline. Флаг политики `auto_promote` делает это без оператора.

Инструменты `control_*` работают только в репозитории с меткой
`grid.workshop=true`, у агентов нет git-инструментов записи, а в `routing.yaml`
хоста администратора нет. Поэтому изменить рабочую копию он не может.
Подробности в `examples/system-admin/README.md`.

## Оценка по сценариям

HTTP-проверки подтверждают только, что кандидат запускается. Сценарий — это одно
сообщение в чат кандидата через `/api/chat/ws/<id>` с детерминированными
ожиданиями:

```json
{"name": "route-video", "message": "Нарежь превью из inputs/event.mp4", "system": "video",
 "agent": "video_director", "tools_called": ["call_video_annotator"],
 "tools_not_called": ["video_render_cutlist"], "output_matches": "(?i)превью",
 "timeout_seconds": 240}
```

Верификатор (`grid_control/verifier.py`, только стандартная библиотека) читает
поток событий: `routed` (система и агент), шаги `step` вида `tool` (вызванные
инструменты), `final_output` или `token` (ответ), `done`. Если сценарий проверяет
только маршрутизацию, ход останавливается сразу после `routed`, и агент не тратит
токены на саму задачу. Результат сценария — ещё одна булева проверка с именем
`scenario:<name>`, поэтому правило решения не меняется: все проверки кандидата
проходят во всех повторах, и прирост не ниже `min_improvement`. LLM-судьи нет.

В политике два набора:

* `scenarios` — приёмочный, закрытый. API мастерской отдаёт по нему только
  прошёл/не прошёл, без объяснений, которые раскрыли бы ожидания. Полные
  подробности видит оператор в `grid-control show`.
* `dev_scenarios` — открытый. `GET /scenarios` показывает его мастерской, а
  `POST /trials` (инструмент `control_trial`) прогоняет на нём снимок
  незавершённой работы один раз и возвращает подробности по каждому сценарию:
  куда ушло сообщение, какие инструменты вызваны, начало ответа. Испытание ничего
  не решает и не может быть продвинуто.

Кандидату для сценариев нужна модель. `egress_hosts` в политике запускает рядом с
кандидатом прокси (`grid_control/egress.py`): кандидат остаётся во внутренней
сети, а наружу проходит только `CONNECT` на порт 443 к перечисленным хостам.
Ключи передаются по именам из `environment_names`. Пример политики с обоими
наборами — `grid_control/policy.example.json`. Это пример: настоящий закрытый
набор храните вне репозитория, иначе мастерская видит его в своём клоне.

Стоимость эксперимента примерно `(checks + scenarios) × repetitions × 2`
прогонов. Для сценариев маршрутизации это один вызов роутера на сценарий.

## Следующие части полного цикла

Нужны входящие из рабочей установки (провалы и откаты маршрутизации превращаются
в черновики сценариев, которые утверждает оператор) и история экспериментов,
доступная администратору, чтобы он не повторял отвергнутые гипотезы.

API контроллера принимает только коммиты (SHA и git bundle) и никогда не
принимает произвольные команды хоста, пути mount или настройки привилегий.

`promoted` переносит ветку `stable`, но пока не пересобирает и не перезапускает
рабочую установку. Для этого нужен постоянный
маршрутизатор перед web chat: новые сессии идут в новую версию, текущие заканчивают
работу в старой. Откат образа и откат данных — разные операции. Миграции хранилищ
нужно проверять отдельно на копиях, иначе старый контейнер может не прочитать
данные новой версии.
