# Перезапуск сервера и продолжение запросов

Кнопка **Accounts → Server → Restart server** доступна администратору при запуске
через `grid-web-chat` или `python -m web_chat`. Встроенное ASGI-приложение без
обработчика перезапуска показывает кнопку недоступной. API проверяет роль и
Origin, не принимает команды или имя сервиса от клиента.

## Как работает управляемый перезапуск

1. Сервер прекращает принимать новую работу и изменения данных. Stop и
   согласование ожидающих действий остаются доступны.
2. Текущие запросы останавливаются **после шага**: ответ модели и вызванные им
   инструменты заканчиваются, результаты сохраняются в SDK-сессии. Подготовка
   агента, фоновые операции и анализы отзывов должны завершиться. Принудительного
   тайм-аута нет: перезапуск может ждать долгий инструмент.
3. История сохраняется с проверкой ошибок записи и `fsync`. В
   `<data-dir>/server_restart.json` атомарно записываются пользователь, чат,
   исходный `run_id` и способ продолжения. В режиме без аккаунтов файл находится
   в каталоге логов. Ошибка записи отменяет выключение сервера.
4. Uvicorn штатно закрывает соединения и ресурсы. Процесс загружает код заново
   через тот же Python и `-m web_chat` с прежними аргументами. Права на управление
   systemd или произвольные команды для кнопки не нужны.
5. При запуске сервер продолжает сохранённые запросы с тем же агентом и его
   сессией, даже если браузер закрыт. Продолжение уже принятого запроса не
   расходует ещё один запрос дневного лимита. Очередь следующих сообщений затем
   выполняется обычным способом.
6. Браузер обнаруживает новый процесс и подключается к запросу. Страница не
   перезагружается, несохранённый черновик остаётся на месте. Авторизация
   сохраняется благодаря постоянным сессиям аккаунтов.

Автоматически продолжаются только запросы, приостановленные этим перезапуском.
Пользовательский Stop, завершённый ответ, отключённый/удалённый аккаунт или новый
запуск в том же чате не возобновляют прежнюю работу. Конфигурация системы должна
остаться доступной после обновления. Ошибки восстановления отражаются в панели
сервера и журнале; неуспешные записи сохраняются для следующего запуска.
Пользователь также может продолжить такой чат вручную.

## Ограничения при аварии

Механизм относится к кнопке, а не к `kill -9`, потере питания, перезагрузке ОС
или прямому `systemctl restart`, оборвавшему работу. Для этих случаев остаются
существующие журналы и ручное «Продолжить».

Обрыв между внешним действием и записью результата оставляет неизвестный исход:
например, письмо уже отправлено, но подтверждение не сохранено. Такие вызовы
инструментов автоматически не повторяются. Контрольная точка сохраняет историю
и результаты завершённого шага, но не состояние Python-процесса, незавершённого
сетевого запроса или каждый токен потока. Идентичный дальнейший ответ модели
после продолжения не гарантируется.

## Как перезапускать интерфейс немедленно

Следующий архитектурный шаг — вынести агентов в отдельные worker-процессы,
независимые от HTTP/WebSocket-сервера:

- Записывать принятый запрос в постоянную очередь до подтверждения браузеру.
  Хранить владельца, `run_id`, систему, состояние и контрольную точку.
- Выдавать worker аренду задания с heartbeat и fencing token, чтобы только один
  исполнитель мог записывать результат. Перезапуск интерфейса тогда не прерывает
  модель и инструменты.
- Сохранять события потока с возрастающим номером. После переподключения браузер
  получает события после последнего подтверждённого номера.
- Для внешних действий записывать намерение и результат, передавать idempotency
  key, когда API это поддерживает. Неизвестный исход проверять по внешнему
  состоянию или передавать человеку, а не повторять вызов.
- Проверить отказы до/после сохранения запроса, внешнего действия, сохранения
  результата и подтверждения клиенту.

Это позволит независимо перезапускать интерфейс и восстанавливать задания после
падения worker. Однократное внешнее действие всё равно зависит от возможностей
инструмента: для произвольной shell-команды такую гарантию дать нельзя.
