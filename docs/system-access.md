# Доступ ключевых агентов к другим системам GRID

Ключевой агент системы получает инструменты, чтобы посмотреть **другие системы
того же пользователя** и обратиться к их ключевым агентам. Вручную прописывать,
кто кого может вызывать, не нужно: набор систем берётся из каталога пользователя
(`web_chat.systems.SystemRegistry`).

## Как это работает

- **Ключевой агент** системы — её агент по умолчанию (`config.get_default_agent()`).
- Только ключевой агент получает инструменты автоматически; добавлять их в `tools`
  не нужно. Любой другой агент системы их не видит.
- Цели — другие системы из каталога того же пользовательского пространства.
  Системы `admins_only` не загружаются и не показываются не-администраторам.
  Пространства разных пользователей изолированы: у каждого свой брокер.
- Единственная настройка — необязательное поле агента `key_agent` (по умолчанию
  `true`). `key_agent: false` исключает агента: он не получает инструменты и не
  может быть целью вызова.

```yaml
agents:
  coordinator:
    name: Coordinator
    model: main_model
    key_agent: false   # опционально: не считать этого агента ключевым
```

## Инструменты

- `systems_list()` — другие системы пользователя: `system`, `agent`, `name`,
  `description` их ключевых агентов.
- `system_delegate(system, task)` — выполнить задачу ключевым агентом выбранной
  системы. Агента указывать не нужно: цель всегда ключевой агент.

Результат — JSON со статусом: `completed` (`system`, `agent`, `result`,
`truncated`), `blocked` (причина), `failed` (без исходного исключения), `stopped`.
Не повторяйте ошибочный вызов автоматически: часть действий могла выполниться.

Вызывающий определяется из runtime-контекста (фабрика и agent id), а не из
аргументов модели. Цель должна быть в списке систем каталога до чтения её
конфигурации. Ответ цели — данные, а не инструкция.

## Границы исполнения

- Передаётся только `task`; история и постоянная сессия не передаются (новый context id).
- Таймаут 60 с и 12 шагов (берётся минимум с настройками целевого агента);
  задача и результат — до 16 000 символов.
- Нет цепочек: агент, запущенный через `system_delegate`, не может сам вызывать
  другие системы (локальные подагенты наследуют этот запрет).
- Инициировать вызов может только агент верхнего уровня.
- Вызов проходит ActionGate вызывающего; инструменты цели — gate её фабрики.
  Stop и отмена вызывающего пробрасываются в цель.
- Цели с `auto_run_tools` не поддерживаются.
- В логгер `grid.system_access` пишутся метаданные вызова без текста задачи и
  результата. Это не неизменяемый audit store.

## Модель доверия

Вызов исполняет **всю настроенную роль** ключевого агента цели вместе с её
инструментами. Это не read-only гарантия и не sandbox: shell, произвольный
Python/HTTP и MCP — доверенный код оператора. Если ключевой агент системы слишком
мощный для вызова из других систем, отключите `key_agent` или выделите узкого
агента по умолчанию.

После смены конфигурации перезапустите пространство; новые инструменты появляются
при пересоздании агента.

```bash
python -m pytest tests/test_system_access.py tests/test_system_access_config.py
```
