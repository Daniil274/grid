# Workspace: управление жизненным циклом, а не дисциплина агентов

## Решение

Рекомендуется встроенный менеджер артефактов Grid: он создаёт рабочую область запуска, регистрирует результаты и управляет их жизненным циклом. Инструкции агентам и ограничения доступа остаются вспомогательными, не основным механизмом порядка.

Это предложение архитектуры; миграция и автоматическая уборка не реализованы и не запускались.

## Что обнаружено

В корне /workspace смешаны продукт grid/ (отдельный репозиторий), uploads/, индексы и состояние агентов, тестовые C-программы и бинарники, графики и результаты экспериментов. В Grid присутствует живой .grid/timeline.db. У корневого репозитория нет коммитов; grid/ не отслеживается им. Некоторые uploads совпадают по содержимому. Нельзя считать ни неизвестные файлы, ни дубликаты мусором.

## Архитектура

- Существующие репозитории остаются на месте и защищаются от уборки. Не переносить grid/ в src/ ради косметики.
- Grid автоматически выделяет `artifacts/<run-id>/work/` для временной работы запуска и `artifacts/<run-id>/outputs/` для результатов. Привязка к разговору, задаче и запуску хранится в реестре.
- Пользователь видит результаты в библиотеке артефактов: имя, тип, происхождение, размер, дата, задача, статус «временный / результат / закреплённый / в корзине».
- Runtime (.grid, .beads), индексы и исходные репозитории — отдельная защищённая категория. Не перемещать активные базы и не включать их в GC.
- Загрузки пользователя неизменяемы и никогда не удаляются автоматически. Возможная дедупликация — через SHA-256 blob + ссылки с исходными именами, только после отдельной миграции.
- Классификация задаётся при создании результата. Неизвестный файл по умолчанию сохраняется и не подлежит автоматической уборке; расширение файла не определяет его ценность.

## Как обеспечить порядок без ограничения workspace

Grid задаёт рабочий каталог запуска и пути сохранения результатов в собственных инструментах и среде исполнения. Агент сохраняет доступ к проекту; это не sandbox. Записи вне выделенной зоны учитываются как неизвестные, показываются для ревью и не перемещаются автоматически. Таким образом механизм снижает загрязнение по умолчанию, но не обещает полный контроль произвольных shell-записей.

Реестр лучше реализовать как транзакционную таблицу в существующем хранилище Grid: одновременные агенты не должны переписывать единый JSON-манифест без блокировок. Классификация git и retention независимы: исходники не скрываются автоматически в .gitignore. Применим отдельный additive блок только для известных runtime/cache/artifact зон.

## Уборка и восстановление

1. Dry-run показывает кандидатов и причины. Кандидаты — только явно временные, неактивные и незакреплённые артефакты старше TTL.
2. GC переносит кандидатов в `.workspace/trash/<operation-id>/`, сохраняет оригинальный путь и журнал. Не следует символическим ссылкам и не пересекает границы защищённых репозиториев.
3. Restore восстанавливает файл; при конфликте не перезаписывает существующее содержимое.
4. Окончательное purge — отдельная явная операция пользователя. Автоматическое физическое удаление по умолчанию выключено.
5. Сбои между переносом и обновлением реестра восстанавливаются по журналу операции.

## Поэтапное внедрение

1. Реестр и обзор использования места, без перемещений. Все старые файлы protected/pinned.
2. Новые запуски используют run-scoped каталоги; выдаваемые пользователю результаты закрепляются.
3. UI библиотеки: поиск по задаче/разговору, pin, экспорт, dry-run уборки.
4. Только после ревью — корзина, восстановление и opt-in retention временных результатов.

Не запускать `git clean -xfd`: в текущей структуре он способен удалить вложенный продукт и пользовательские файлы. Первый коммит/резервная копия — отдельный согласованный шаг, не автоматическая часть наведения порядка.

## Критерии приёмки будущей реализации

- Исторические, загруженные и неизвестные файлы не удаляются.
- GC не затрагивает активные запуски, исходники, pinned и runtime.
- Конкурентные записи и аварийное завершение не теряют реестр.
- Перенос обратим, восстановление не перезаписывает конфликтующий файл.
- Каждый результат имеет provenance; UI показывает место и причины retention.
- Базовый порядок достигается без новых запретов доступа и без надежды исключительно на инструкции агентам.
