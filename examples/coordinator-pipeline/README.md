# Autonomous coordinator pipeline

Исполнимый пример Grid: координатор выбирает следующий шаг, фоновые workers
выполняют ограниченные задачи, runtime сохраняет попытки и контролирует приёмку.
Codex, MCP-сервер и beads для запуска не нужны.

## Быстрый запуск без API

Из корня репозитория, в окружении с установленными зависимостями Grid:

```powershell
python examples/coordinator-pipeline/run.py --demo
```

Демонстрация создаёт отдельную папку в `runs/`. Сценарные агенты записывают
`events.py`, воспроизводят повторную обработку события, отклоняют первую попытку,
исправляют её и запускают три проверки. Используется настоящий
`BackgroundAgentSupervisor` и runtime, но решения агентов заданы кодом.
Это проверка механики, а не оценка качества LLM.

## Запуск с моделью

```powershell
Copy-Item examples/coordinator-pipeline/config.yaml.example examples/coordinator-pipeline/local.yaml
# В local.yaml задайте endpoint, api_key_env и реальный models.default.name.
# Передайте API-ключ через указанную переменную окружения.
python examples/coordinator-pipeline/run.py --config examples/coordinator-pipeline/local.yaml --check
python examples/coordinator-pipeline/run.py --config examples/coordinator-pipeline/local.yaml --workdir C:/path/to/project "Исправь повторную обработку событий и проверь результат"
```

`--check` проверяет конфиг, каталог инструментов и схемы функций без вызовов API.
Он не проверяет ключ, доступность провайдера или существование модели.
Можно использовать другой конфиг Grid с агентом `coordinator`, либо указать
`--model KEY`. Workers выбирают модели того же провайдера из актуального каталога.
Инструменты загружаются из `examples/coder/tools` относительно этого репозитория.

Параметры: `--deadline 900`, `--max-attempts 3`, `--max-launches 20`,
`--concurrency 4`, `--state-dir PATH`. Общий deadline включает рассуждение
координатора, ожидание очереди и работу агентов. Каждый worker имеет собственный
таймаут в пределах оставшегося времени. Код выхода: 0 — completed, 1 — незавершённая
работа/ошибка, 130 — прерывание пользователем.

## Как устроено

| Компонент | Ответственность |
|---|---|
| `run.py` | CLI: открывает прогон и запускает автономного LLM-координатора |
| `tools/pipeline_tools.py` | Те же инструменты как обычные тулы Grid (для чата и роутера) |
| `core/pipeline_runtime.py` | Контракты, попытки, доступ к общей папке, приёмка, сохранение состояния |
| `core/background_agents.py` | Фоновые workers, очередь, ожидание события, отмена и таймаут |
| `skills/coordinator.md` | Короткий цикл принятия решений |
| `skills/worker.md` | Общий протокол исполнителя и формат доказательств |
| `offline.py` | Воспроизводимый сценарий дефект → исправление |

Координатор получает `file_read`, `glob_tool`, `grep_tool` и восемь инструментов
runtime: `pipeline_task`, `pipeline_wait`, `pipeline_inspect`, `pipeline_review`,
`pipeline_retry`, `pipeline_interrupt`, `pipeline_finish`, `pipeline_block`. Он может проверить артефакты лично.
Нет обязательной разведки, фиксированной цепочки ролей или рекурсивной делегации.

## Запуск из чата и через роутер

Инструменты те же самые, поэтому пайплайн доступен не только из CLI. В
`config.yaml` объявлен агент `pipeline_coordinator` — единственный routable агент
этой системы, поэтому `agent_chat.py` без `--agent/--config` направляет к нему
крупные многошаговые задачи по каталогу `routing.yaml` (система `pipeline`).

```powershell
python agent_chat.py            # роутер выбирает систему по сообщению
python agent_chat.py --config examples/coordinator-pipeline/config.yaml --agent pipeline_coordinator
```

Разница только в том, кто открывает прогон: в CLI это делает `run.py`, в чате —
сам координатор вызовом `pipeline_start` с целью пользователя. Прогон один на
фабрику: следующий начинается после `pipeline_finish` или `pipeline_block`.
Журнал пишется в `<logs_directory>/pipeline-runs/<id>.json`. Beads-координатор
(`coordinator`) остаётся в конфиге, но в маршрутизации не участвует — вызывайте
его явно через `--agent coordinator`.

Задание содержит цель, область, входы, критерии готовности и ограничения. Отдельно
задаются модель, инструменты, тип работы и таймаут. Runtime добавляет общий
протокол, предыдущую попытку при исправлении и кандидат при проверке.

### Доступ к рабочей папке

- `research`: только чтение/поиск; несколько workers могут работать одновременно.
- `change`: чтение, запись, редактирование и команды; исключительный доступ.
- `verification`: чтение/поиск и команды проверок; исключительный доступ.

Если папка занята несовместимой работой, запуск отклоняется. Координатор ждёт
завершения текущей волны и повторяет запуск. Новое изменение нельзя начать до
приёмки предыдущего; отклонённое исправляется через `pipeline_retry` того же задания.
Параллельная запись и worktrees в этой версии отсутствуют.

### Приёмка

`completed` у worker означает только, что выполнение завершилось. Для приёмки
изменения нужна отдельная завершённая verification-задача, связанная с точной
попыткой изменения, и положительное решение координатора по этой проверке.
Решения содержат свидетельства и не переписываются. Повтор сохраняет историю.

При провале проверки координатор отклоняет проверку и изменение, повторяет
изменение с конкретным замечанием, затем создаёт новую проверку. Старую нельзя
использовать для приёмки новой попытки. `pipeline_finish` отклоняется, если остались
работающие агенты или неразрешённые задания. Простые ответы допустимы без workers.

Runtime проверяет состояния и связи, но не может доказать правдивость отчёта или
полноту покрытия цели. Это ответственность координатора. Профили инструментов
не являются sandbox: `bash_tool` запускает произвольные команды. Проверяющему
инструкцией запрещено исправлять продуктовый код. Не запускайте одновременно
другие изменяющие процессы в той же рабочей папке.

### Состояние и остановка

Журнал прогона атомарно обновляется при запуске, завершении и приёмке. В нём
сохраняются контракт, идентификаторы workers, результаты, ошибки, замечания,
лимиты и финальный статус. Не храните там секреты. Результат worker ограничен
лимитом supervisor (20 000 символов); крупные артефакты передавайте файлами.

Возврат координатора без `pipeline_finish`/`pipeline_block` считается blocked. При deadline,
ошибке или Ctrl+C runtime отменяет незавершённых workers и сохраняет статус.
Отмена не откатывает файлы и не гарантирует остановку уже запущенных внешних
процессов. Перед повтором нужно проверить частично выполненную работу.

Файл состояния — журнал для разбора, не checkpoint процесса: автоматического
возобновления после аварии нет. При аварийном завершении запись может остаться
`running`; новый запуск создаёт отдельный журнал и не повторяет старые задания сам.

## Переход со старого примера

Используйте `run.py` и новый `config.yaml.example`. Старый локальный `config.yaml`
не изменяется автоматически: он мог содержать пользовательские модели и ключи.
Скопируйте из него настройки провайдера/моделей, если они нужны. Прежние
`orchestrate`, `call_coordinator`, beads и `init_tools` этому примеру не нужны.
Старые механизмы Grid вне примера продолжают работать.
