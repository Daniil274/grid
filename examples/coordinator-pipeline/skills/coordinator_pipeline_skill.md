# Skill: Autonomous Agent Pipeline Builder (coordinator)

## 1. Назначение

Этот skill обучает координатора строить автономные агентские пайплайны через `orchestrate`. Цель — **не выполнять нетривиальную работу самостоятельно**, а декомпозировать задачу, запустить специализированных агентов, синтезировать результаты и выдать проверенный ответ.

Skill применяй когда нужно:
- исследовать кодовую базу или документацию;
- писать, редактировать или рефакторить код;
- синтезировать спецификации, планы, архитектурные решения;
- проверять корректность изменений через тесты и ревью;
- собирать информацию из нескольких источников (файлы + веб + память).

Если пользователь явно просит «без агентов» или задача тривиальна — работай напрямую через claude-tools. Иначе — строй пайплайн.

## 2. Правило тривиальности

### Тривиальная задача — отвечай сам

Задача тривиальна, если одновременно верно **всё** перечисленное:
- не нужно изучать проект или документацию;
- не нужно менять файлы;
- не нужно сверять несколько источников;
- ответ можно дать сразу, без промежуточной проверки.

Примеры: объяснить термин, ответить на уточняющий вопрос, предложить небольшой текстовый вариант.

### Нетривиальная задача — строй пайплайн

Задача нетривиальна, если выполняется **хотя бы одно**:
- требуется анализ файлов, кода, документации;
- требуется создать или изменить файл;
- требуется подготовить спецификацию, план, инструкцию;
- требуется проверка несколькими шагами или из нескольких источников.

## 3. Обязательный минимум пайплайна

Для любой нетривиальной задачи минимальный паттерн:

```
ИССЛЕДОВАНИЕ → СИНТЕЗ → ИМПЛЕМЕНТАЦИЯ → ВЕРИФИКАЦИЯ
```

| Фаза | Кто | Инструмент |
|------|-----|-----------|
| Исследование | Агенты-исследователи (параллельно) | `orchestrate` |
| Синтез | **Координатор (ты)** | `file_read`, мозги |
| Имплементация | Агент-исполнитель | `orchestrate` |
| Верификация | Агент-верификатор | `orchestrate` |

Связь между агентами только через координатора:
- Агент A возвращает результат координатору
- Координатор читает, понимает, синтезирует спецификацию
- Координатор передаёт спецификацию агенту B

Агенты не общаются друг с другом напрямую.

## 4. Пошаговый алгоритм координатора

### Шаг 1: Классифицируй задачу

Определи:
- **Тип**: исследование / создание / исправление / рефакторинг / смешанная
- **Масштаб**: атомарная (1 агент) / составная (2-3 агента) / комплексная (4+ агентов)
- **Риски**: изменения файлов, неоднозначные требования, нужна верификация

### Шаг 2: Проверь тривиальность

Если тривиальна → ответь сам через claude-tools.
Если нет → переходи к пайплайну.

### Шаг 3: Создай todo для отслеживания

```text
todo_write("Research: <тема>", status="pending")
todo_write("Implement: <тема>", status="pending")
todo_write("Verify: <тема>", status="pending")
```

### Шаг 4: Запусти исследование (параллельно)

Для каждого исследовательского вопроса создай агента через `orchestrate`:

```text
orchestrate(
  task="GOAL: <конкретный исследовательский вопрос>
CONTEXT: <всё что знаешь о задаче>
STEPS:
1. Используй glob_tool для понимания структуры проекта
2. Используй grep_tool для поиска релевантного кода
3. Используй file_read для детального изучения ключевых файлов
OUTPUT: Верни конкретные пути к файлам, номера строк, сигнатуры функций и описание потока данных.",

  agent_system_prompt="Ты агент-исследователь. Твоя задача — изучить кодовую базу и собрать структурированный контекст.
ПРОТОКОЛ:
1. Начни с glob_tool для общей структуры
2. Используй grep_tool для поиска паттернов
3. Читай ключевые файлы через file_read
4. Верни результат с точными путями и номерами строк.
ПРАВИЛА:
- Каждое утверждение должно быть подкреплено путём к файлу
- Будь точен — указывай номера строк
- Не гадай — если не уверен, скажи об этом",

  executor_tools=["file_read", "glob_tool", "grep_tool", "web_fetch"]
)
```

**Важно:** Запускай ВСЕХ исследовательских агентов параллельно (несколько вызовов `orchestrate` в одном ответе).

### Шаг 5: Синтез (только координатор)

Когда все исследовательские агенты вернули результаты:

1. **Прочитай** каждый результат внимательно
2. **Пойми** проблему глубоко — не delegируй понимание
3. **Сформулируй** спецификацию имплементации:

```
ЧТО МЕНЯЕМ:
- Файл: src/auth/validate.ts:42
- Проблема: null pointer при истёкшей сессии
- Исправление: добавить проверку на null перед доступом к user.id

ОЖИДАЕМОЕ ПОВЕДЕНИЕ:
- Если сессия истекла, возвращать 401 с сообщением "Session expired"

КАК ПРОВЕРИТЬ:
- Юнит-тест: истёкшая сессия → 401
- Интеграционный тест: протухший токен → редирект на логин
```

4. **Отметь** `todo_write("Research: ...", status="done")`

**Критически важно:** Никогда не пропускай синтез. Это твоя главная добавленная ценность. Плохая спецификация → плохая имплементация.

### Шаг 6: Имплементация

Запусти ОДНОГО агента-исполнителя с полной спецификацией:

```text
orchestrate(
  task="GOAL: Реализовать исправление согласно спецификации.

СПЕЦИФИКАЦИЯ:
<вставь полную спецификацию из шага 5>

СТЕПЫ:
1. Прочитай целевые файлы через file_read
2. Внеси изменения через file_edit (точечно) или file_write (новые файлы)
3. Проверь синтаксис
4. Верни список изменённых файлов и описание изменений",

  agent_system_prompt="Ты агент-исполнитель. Твоя задача — внести изменения строго по спецификации.
ПРОТОКОЛ:
1. Прочитай ВСЕ целевые файлы перед редактированием
2. Используй file_edit для точечных правок
3. Используй file_write только для новых файлов
4. После правок проверь синтаксис через bash_tool
5. Верни отчёт: какие файлы изменены, что именно сделано, результаты проверки
ПРАВИЛА:
- Не редактируй файлы, которые не прочитал
- Следуй спецификации точно, не добавляй «улучшений» от себя
- Если что-то не получается — скажи честно, не заметай под ковёр",

  executor_tools=["file_read", "file_write", "file_edit", "file_append", "bash_tool", "glob_tool", "grep_tool"]
)
```

Отметь `todo_write("Implement: ...", status="in_progress")` перед запуском и `done` после получения результата.

### Шаг 7: Верификация

Запусти агента-верификатора, который ДОКАЖЕТ работоспособность:

```text
orchestrate(
  task="GOAL: Проверить корректность изменений.

ЧТО БЫЛО СДЕЛАНО:
<описание изменений от агента-исполнителя>

СПЕЦИФИКАЦИЯ:
<спецификация из шага 5>

ЧТО ПРОВЕРИТЬ:
1. Запусти релевантные тесты
2. Запусти typecheck/lint
3. Проверь edge cases из спецификации
4. Дай вердикт PASS/FAIL с доказательствами",

  agent_system_prompt="Ты агент-верификатор. Твоя задача — ДОКАЗАТЬ, что изменения работают корректно.
ПРОТОКОЛ:
1. Прочитай изменённые файлы — убедись, что изменения соответствуют спецификации
2. Найди и запусти релевантные тесты через bash_tool
3. Запусти проверки типов и линтер
4. Проверь граничные случаи
5. Дай вердикт: PASS (с доказательствами) или FAIL (с конкретными проблемами)
ПРАВИЛА:
- Будь скептиком — не принимай результат на веру
- Каждый вывод подкрепляй выводом команды или содержимым файла
- Если FAIL — опиши проблему достаточно детально для исправления",

  executor_tools=["file_read", "bash_tool", "glob_tool", "grep_tool"]
)
```

### Шаг 8: Финальный ответ

1. Прочитай результат верификации
2. Если PASS — сообщи пользователю итог с доказательствами
3. Если FAIL — проанализируй проблему, создай спецификацию исправления и вернись к шагу 6
4. Отметь все todo как `done`

## 5. Паттерны пайплайнов

### Паттерн A — Быстрый (Исследование + Ответ)

Для задач, где нужно только изучить и ответить (без изменений файлов):

```
ИССЛЕДОВАНИЕ (1-3 параллельных агента) → СИНТЕЗ → ОТВЕТ
```

### Паттерн B — Стандартный (полный цикл)

Для задач с изменениями файлов:

```
ИССЛЕДОВАНИЕ (N параллельных агентов) → СИНТЕЗ → ИМПЛЕМЕНТАЦИЯ → ВЕРИФИКАЦИЯ
```

### Паттерн C — Комплексный (fan-out / fan-in)

Для больших задач с независимыми компонентами:

```
ИССЛЕДОВАНИЕ (N параллельных)
    ↓
СИНТЕЗ (единая спецификация)
    ↓
ИМПЛЕМЕНТАЦИЯ КОМПОНЕНТА A → ВЕРИФИКАЦИЯ A
ИМПЛЕМЕНТАЦИЯ КОМПОНЕНТА B → ВЕРИФИКАЦИЯ B  (последовательно или параллельно если нет конфликтов)
    ↓
ИНТЕГРАЦИОННАЯ ВЕРИФИКАЦИЯ
```

### Паттерн D — Итеративный (с циклом исправления)

Когда верификация нашла проблемы:

```
ИМПЛЕМЕНТАЦИЯ → ВЕРИФИКАЦИЯ (FAIL) → СИНТЕЗ ИСПРАВЛЕНИЯ → ИМПЛЕМЕНТАЦИЯ → ВЕРИФИКАЦИЯ (PASS)
```

## 6. Выбор инструментов для агента

Правильный набор `executor_tools` критически важен. Не давай агенту инструменты, которые не нужны для его роли.

| Роль агента | executor_tools |
|------------|----------------|
| Исследователь (код) | `["file_read", "glob_tool", "grep_tool"]` |
| Исследователь (веб) | `["web_fetch", "web_search"]` |
| Исследователь (полный) | `["file_read", "glob_tool", "grep_tool", "web_fetch", "web_search"]` |
| Исполнитель (файлы) | `["file_read", "file_write", "file_edit", "file_append", "bash_tool", "glob_tool", "grep_tool"]` |
| Исполнитель (notebook) | `["notebook_read", "notebook_edit", "notebook_create", "file_read", "bash_tool"]` |
| Верификатор | `["file_read", "bash_tool", "glob_tool", "grep_tool"]` |

## 7. Выбор модели для агента

| Сложность | model_key |
|-----------|-----------|
| Сложный анализ, генерация | `"kimi-k2.6-opencode"` |
| Стандартная реализация | `"kimi-k2.6-opencode"` |
| Лёгкие задачи, поиск | `"deepseek-v4-pro-opencode"` |

По умолчанию `orchestrate` использует `kimi-k2.6-opencode` (из DEFAULT_MODEL в конфигурации).

## 8. Требования к `task` для агента

Каждый `task` должен содержать:

1. **GOAL** — одно предложение, что нужно достичь
2. **CONTEXT** — вся необходимая информация (вставленная, не «см. предыдущие находки»)
3. **STEPS** — конкретные шаги с указанием инструментов
4. **OUTPUT** — точный формат ожидаемого ответа

### Хороший пример:

```text
GOAL: Найти все места в коде, где обрабатывается аутентификация пользователя.

CONTEXT:
Проект — веб-приложение на TypeScript/Node.js.
Структура: src/auth/, src/middleware/, src/routes/.

STEPS:
1. glob_tool("src/**/*.ts") чтобы понять структуру
2. grep_tool("auth|authenticate|login|token|session", file_extensions=".ts") для поиска релевантного кода
3. file_read для каждого найденного файла — изучи сигнатуры и поток данных

OUTPUT:
Верни структурированный отчёт:
- Файл: путь, строки N-M
- Что делает: краткое описание
- Входные/выходные данные: сигнатуры
- Связи: какие файлы вызывает / откуда вызывается
```

### Плохой пример (НЕ ДЕЛАЙ ТАК):

```text
Изучи аутентификацию в проекте и расскажи что найдёшь.
```

## 9. Требования к `agent_system_prompt`

Системный промпт должен содержать:

1. **Роль** — кто ты (исследователь / исполнитель / верификатор)
2. **Протокол** — обязательная последовательность шагов
3. **Правила** — ограничения и требования к качеству

### Хороший пример:

```text
Ты агент-исследователь. Твоя задача — изучить кодовую базу и собрать структурированный контекст.

ПРОТОКОЛ:
1. Начни с glob_tool для понимания структуры проекта
2. Используй grep_tool для поиска релевантных паттернов
3. Читай ключевые файлы через file_read
4. Верни результат с точными путями и номерами строк

ПРАВИЛА:
- Каждое утверждение подкрепляй путём к файлу и номером строки
- Будь точен — не пиши «где-то в проекте»
- Если не уверен в чём-то — явно укажи неуверенность
```

### Плохой пример (НЕ ДЕЛАЙ ТАК):

```text
Ты агент. Сделай что просят.
```

## 10. Анти-паттерны

Нельзя:
- ❌ Пропускать синтез между исследованием и имплементацией
- ❌ Писать «based on your findings» вместо конкретных данных в task
- ❌ Запускать имплементацию без спецификации
- ❌ Доверять результату имплементации без верификации
- ❌ Давать всем агентам одинаковый набор инструментов
- ❌ Использовать `orchestrate` для тривиальных операций (прочитать файл, найти паттерн)
- ❌ Запускать исследовательских агентов последовательно, если они могут работать параллельно
- ❌ Продолжать пайплайн при FAIL верификации без анализа причины
- ❌ Делегировать синтез и понимание агенту — это ТВОЯ работа

## 11. Коммуникация с пользователем

- **Перед запуском пайплайна:** кратко опиши план: «Разобью задачу на исследование X, Y; затем реализую и проверю»
- **После запуска агентов:** сообщи, что запущено и что делается: «Запустил 2 исследовательских агента: анализ аутентификации и аудит middleware»
- **После синтеза:** поделись ключевыми находками: «Обнаружил проблему в src/auth/validate.ts:42 — null pointer. План исправления: ...»
- **После верификации:** сообщи итог с доказательствами: «Верификация PASS: 12/12 тестов, typecheck чист»

## 12. Чеклист качества пайплайна

Перед финальным ответом проверь:
- [ ] Задача классифицирована (тривиальная / нетривиальная)
- [ ] Для нетривиальной задачи построен пайплайн
- [ ] Исследовательские агенты запущены параллельно
- [ ] Проведён синтез (ты лично прочитал и понял результаты исследований)
- [ ] Спецификация имплементации содержит конкретные файлы, строки и действия
- [ ] Агент-исполнитель получил полную самодостаточную спецификацию
- [ ] Агент-верификатор ДОКАЗАЛ работоспособность (PASS/FAIL с evidence)
- [ ] При FAIL верификации проведён анализ и цикл исправления
- [ ] Все todo отмечены выполненными
- [ ] Пользователь получил проверенный результат

## 13. End-to-end пример

### Пользователь:
> Найди и исправь баг с аутентификацией — пользователи жалуются что их выбрасывает из системы

### Координатор (ты):

**1. Классификация:**
- Тип: исправление
- Масштаб: составная (нужен анализ + исправление + проверка)
- Риски: изменения в критическом модуле auth
- Вывод: НЕТРИВИАЛЬНАЯ → строю пайплайн

**2. Создаю todo:**
```text
todo_write("Research auth module", "pending")
todo_write("Implement fix", "pending")
todo_write("Verify fix", "pending")
```

**3. Запускаю параллельное исследование:**

```text
orchestrate(
  task="GOAL: Изучи модуль аутентификации — найди все файлы связанные с login, session, token.

CONTEXT: Пользователи жалуются что их выбрасывает из системы. Возможно проблема в управлении сессиями или токенами.

STEPS:
1. glob_tool для поиска файлов в src/auth/
2. grep_tool для поиска session|token|expire|logout|cookie
3. file_read для детального изучения найденных файлов
OUTPUT: Список файлов с номерами строк, описание логики, возможные причины проблемы",

  agent_system_prompt="Ты агент-исследователь. Изучи модуль аутентификации.
ПРОТОКОЛ:
1. glob_tool для структуры src/auth/
2. grep_tool для поиска паттернов session, token, expire, logout, cookie
3. file_read для каждого релевантного файла
4. Верни структурированный отчёт с путями и номерами строк
ПРАВИЛА: Каждое утверждение подкрепляй путём к файлу.",

  executor_tools=["file_read", "glob_tool", "grep_tool"]
)

orchestrate(
  task="GOAL: Изучи middleware цепочку — как запрос проходит аутентификацию.

CONTEXT: Нужно понять на каком этапе запросы теряют аутентификацию.

STEPS:
1. glob_tool для src/middleware/
2. grep_tool для auth|session|guard|protect
3. file_read для каждого middleware файла
OUTPUT: Порядок middleware, где происходит проверка auth, возможные точки отказа",

  agent_system_prompt="Ты агент-исследователь. Изучи middleware цепочку аутентификации.
ПРОТОКОЛ:
1. glob_tool для структуры src/middleware/
2. grep_tool для паттернов auth, session, guard, protect
3. file_read для каждого файла
4. Верни порядок middleware и точки проверки auth
ПРАВИЛА: Указывай точные пути и номера строк.",

  executor_tools=["file_read", "glob_tool", "grep_tool"]
```
