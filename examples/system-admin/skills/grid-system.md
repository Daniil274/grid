# Как устроена система Grid

Система — это один конфиг со своими агентами. Живёт в своём каталоге:

```
examples/<name>/
  config.yaml      # провайдеры, модели, инструменты, агенты
  README.md        # назначение, запуск, устройство, ограничения
  skills/*.md      # протоколы, которые подмешиваются в промпт агента
  tools/*.py       # собственные инструменты системы (если нужны)
  workspace/       # рабочая папка по умолчанию (если нужна)
```

Образцы: `examples/coder` (один агент, много инструментов), `examples/video-editor`
(режиссёр и специалисты через agent-инструменты), `examples/coordinator-pipeline`
(координатор фоновых исполнителей), `examples/windows-computer-use` (свои
инструменты в `tools/`). Прежде чем писать, прочитай близкий образец целиком.

## config.yaml

- `settings`: `default_agent`, `working_directory` (относительно каталога конфига),
  `allow_path_override: true`, лимиты (`max_turns`, `agent_timeout`), `agent_logging`,
  при собственных инструментах `project_tools: {enabled: true, tools_directory: ./tools}`.
- `providers`: `name`, `base_url`, `api_key_env` (имя переменной окружения, не ключ),
  `timeout`, `max_retries`.
- `models`: ключ → `name` у провайдера, `provider`, `temperature`, `max_tokens`,
  `context_window`, `description`. Бери модели, которые уже используются в соседних
  системах: их имена и провайдеры проверены.
- `tools`: каждый инструмент, которым пользуется хоть один агент, объявлен здесь.
  - `type: function` — Python-функция: встроенная (`file_read`, `git_diff`, …, их
    список виден в каталоге систем) или из `tools/` этой системы.
  - `type: agent` — вызов другого агента системы: `target_agent`, `description`,
    `context_strategy: minimal` (бриф передаётся целиком во входе) или `conversation`.
  - `type: mcp` — внешний MCP-сервер: `server_command`.
- `agents`: ключ → `name`, `model` (ключ из `models`), `description`, `tools`,
  `system_skills` (имена файлов из `skills/` без расширения), `custom_prompt`,
  `routable` (false — только для вызова другими агентами).

Конфиг, ссылающийся на необъявленную модель или инструмент, не загрузится вовсе.

## Описания решают маршрутизацию

Роутер читает только `description` системы в `routing.yaml` и `description`
routable-агентов. Хорошее описание называет конкретные задачи и входы
(«видеофайлы mp4/mov: нарезка, субтитры, рендер») и явно говорит, для чего система
НЕ нужна, если рядом есть похожая. Описание — не реклама и не перечень инструментов.
Если в системе один вход, делай routable одного агента, остальных `routable: false`.

## Промпт агента

`custom_prompt` задаёт роль, границы ответственности и признак завершения.
Коротко, по делу, без перечисления инструментов (их описания модель видит сама).
Длинные протоколы выноси в `skills/` — их можно переиспользовать и читать отдельно.
Пиши промпт на языке, на котором система общается с пользователем.

## Собственные инструменты

Файл в `tools/` с функциями под `@function_tool` (из `agents`). Имя функции — имя
инструмента, docstring — его описание для модели: что делает, когда вызывать, что
возвращает. Файлы с `_` в начале имени не загружаются как инструменты — туда кладут
общий код. Инструмент возвращает строку или JSON с результатом, а ошибки сообщает
текстом, не падая. Внешние программы указывай в `requires` записи роутинга.

## Регистрация в routing.yaml

```yaml
routing:
  systems:
    <name>:
      config: examples/<name>/config.yaml
      requires: [ffmpeg]          # только если нужны внешние программы
      description: >-
        ...
```

Меняй только свою запись в `routing.systems`. Секции `settings`, `providers`,
`models` и записи других систем не трогай.

## Готовность

`grid_check_system` возвращает `healthy: true`, система зарегистрирована
(`registered_as` не пустой), README описывает назначение, запуск и ограничения.
Проверка не вызывает модели: ключи, доступность провайдера и качество ответов она
не подтверждает — так и сообщай.
