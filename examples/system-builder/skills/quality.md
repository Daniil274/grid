# Контракт и проверка качества

Начни с ожидаемого пользовательского результата. Уточняй только неизвестное,
от которого зависит архитектура или приёмка. Не спрашивай о технических мелочах.

Выбирай минимальную архитектуру, способную пройти приёмку. Для каждого отдельного
агента объясни пользу: независимая работа, разные инструменты/доступы или проверка.
Мультиагентность сама по себе не критерий качества. Если есть сомнение, сделай
простой baseline и кандидат через builder_fork; запусти builder_evaluate для обоих
и builder_compare на одних и тех же сценариях и бюджетах.
Не жертвуй долей решённых задач ради меньшего числа токенов.

Укажи для каждой роли вход, выход, критерий завершения, поведение при ошибке.
В промптах и навыках реализуй эти контракты, а не просто перечисли роли в YAML.
Делегируй через type: agent с context_strategy: minimal. Передавай постановку,
необходимые факты и пути артефактов. У каждого изменяемого файла должен быть один
владелец; проверяющий читает результат. Запиши это в навыках системы. Повторные
действия должны проверять предыдущий результат и не дублировать внешние эффекты.

`quality.yaml` записывается через builder_write, проверяется строгой схемой.
Пример для агента main, который анализирует текст:

```yaml
version: 1
goal: Подсчитать слова в текстовых файлах
result: JSON-файл result.json с числом слов
acceptance: Число совпадает с контрольным подсчётом, исходный файл сохранён
architecture: single
rationale: Одна операция с одним набором инструментов, делегирование не требуется
roles:
  - agent: main
    purpose: Подсчёт слов и сохранение результата
    inputs: Путь к UTF-8 тексту в рабочей папке
    outputs: result.json и краткая ссылка на него
    acceptance: Валидный JSON с точным числом слов
    failure: Сообщить, что файл не найден, не создавать выдуманный результат
examples:
  - Посчитай слова в input.txt и сохрани result.json
limitations:
  - Только UTF-8 текст; слова разделяются пробелами
failure_behavior: Сохранить исходники, назвать проблемный файл и предложить исправление
repetitions: 2
max_total_seconds: 600
max_total_tokens: 100000
max_total_tool_calls: 200
scenarios:
  - name: count
    category: normal
    message: Посчитай слова в input.txt и сохрани result.json с полем words.
    fixtures:
      input.txt: One two two. Three!
    timeout_seconds: 90
    max_tokens: 20000
    max_tool_calls: 20
    assertions:
      - kind: json_equals
        path: result.json
        value: {words: 4}
      - kind: equals
        path: input.txt
        value: One two two. Three!
  - name: missing
    category: invalid_input
    message: Посчитай слова в missing.txt и сохрани result.json; если файла нет, ответь FILE_NOT_FOUND.
    assertions:
      - kind: contains
        value: FILE_NOT_FOUND
      - kind: absent
        path: result.json
```

Форматы проверок: `contains`, `not_contains`, `equals`, `json_equals` для ответа
(без path) или файла; `csv_equals` для списка объектов строк CSV со строковыми
значениями; `exists`/`absent` для файла. Проверяй содержимое, а не только наличие.
Пустые проверки и произвольный тестовый Python не допускаются.

Категории: normal, ambiguous, invalid_input, failure, repeat, boundary. Категория
сама не инжектирует ошибку: запрос и fixtures должны действительно создавать
проверяемую ситуацию. Каждый сценарий и повтор начинают с чистой среды; repeat
проверяет повторную операцию в рамках одного запроса и её итоговый артефакт.
Успех означает прохождение всех проверок во всех повторах. Для сложной системы
покрой нормальный путь, неоднозначность, плохие данные, частичный сбой и повтор.

Среда: отдельный контейнер и временная папка только с fixtures. Пакеты ставятся
до старта агента, затем сеть контейнера отключается. Сетевые общие инструменты
остаются под серверной политикой; оценивай внешние интеграции на тестовых данных.
Если система требует живую сеть из контейнера, текущий оценщик её не поддерживает:
оставь явный блокер, не имитируй успешный прогон. Модели работают через сервер.

Весь набор ограничен временем и наблюдаемыми токенами/вызовами, включая события
делегированных агентов. Текущий запрос может превысить лимит до прихода usage;
это не жёсткая денежная квота. Если usage отсутствует, соблюдение бюджета не
подтверждено. Денежную стоимость без тарифа не выдумывай.

После провала меняй реализацию по фактам отчёта. Не переписывай ожидаемые значения
под ответ модели. Максимум три цикла исправления; затем объясни оставшийся провал.
Тесты разработки видны builder и не являются независимым экзаменом. Владелец
может добавить свои проверки на Systems → Test; они тоже запускаются и недоступны
для редактирования инструментами builder. Не обходи их отказ изменением контракта.
Пользователю
нужно попробовать собственные примеры и проверить удобство: понятность входов,
этапов, ошибок, ссылок на результат и возможность продолжить после частичного сбоя.

Заверши кратко: ссылка на черновик, что делает, примеры запросов, сколько сценариев
и повторов прошло, время/токены, ограничения и следующий шаг владельца. Различай
«создано», «конфигурация исправна», «пройдено N сценариев» и «включено владельцем».
