# Сопоставление оркестрации Anthropic (Managed Agents — Dynamic workflows) и локального grid

Дата: 2026-10-10. Задача: workspace-y2t. По результатам workspace-7d7 и workspace-vqt, с перепроверкой первичкой и кодом.
Обозначения источников: **[A]** — первичные доки Anthropic (прочитаны целиком), **[G]** — код grid (прочитан напрямую), **[CC]** — Claude Code docs, **[?]** — вторичные/неподтверждённые.

## 1. Идентификация и границы сравнения

Два РАЗНЫХ продукта Anthropic, не смешиваются:
- **Claude Managed Agents — Dynamic workflows** (public beta 2026-10-09): агент пишет программу (workflow), сервер API-платформы исполняет её в фоне как один «workflow run» по фазам, создавая session threads. Источники: https://platform.claude.com/docs/en/managed-agents/workflow-runs и .../multiagent-orchestration (прочитаны целиком, перепроверены). Всюду ниже «Anthropic» = эта поверхность.
- **Claude Code workflows**: локальный CLI surface (`.claude/workflows` scripts, resume/replay, stall-restart до 5 рестартов, `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`, предупреждение >25 агентов / >1.5M токенов, ultracode, `/workflows` UI) — https://code.claude.com/docs/en/workflows. НЕ источник фактов о Managed Agents.

Закрытая облачная реализация Anthropic как код не исследовалась — только публичные доки. Их собственная оговорка «The API doesn't guarantee this number» в первичке относится ТОЛЬКО к числу потоков, работающих одновременно (64), и не покрывает 1000 агентов, 24h и 10 ранов; она зафиксирована как оговорка, а не как проверенное поведение. (Ошибка ранних редакций: оговорка распространялась на «64/1000» — это неверно.)

Разделение статусов по всему документу: **факт** — прочитано в первичке [A] или коде [G] с указанной точкой; **проектная цель** — план §5, не реализовано и не измерено; **измеренное** — только §6 (benchmark ещё не проведён) и данные с пометкой [?].

**grid**: `/workspace/grid` (Python, ~687 файлов); оркестрация = coordinator-агент с meta-tool `orchestrate` (`tools/orchestrator_tools.py:267`) + `parallel` (`tools/parallel_tools.py`) + beads-планирование. Ключевые модули прочитаны: `core/tracing/pipeline_registry.py`, `tools/orchestrator_tools.py`, `core/agent_factory.py`, `core/factory/{turns,tools,auto_run,failures}.py`, `tools/parallel_tools.py`, `core/parallel_lanes.py`, `core/background_agents.py`, `core/tracing/tracer.py`, `grid_control/service.py`, `core/model_access.py`, `core/pricing.py`.

## 2. Ответы на специальные вопросы

### 2.1. PipelineRegistry — исполнительный DAG или трассировка?
**Установлено [G]: ни то, ни другое — это сериализатор + реестр-трассировщик, НЕ планировщик.**
- `run_serialized_step` (`core/tracing/pipeline_registry.py:288`) исполняет шаг сразу (`asyncio.create_task`) под реентерабельным per-pipeline lock (`_enter/_exit_serial_scope`); вложенные вызовы того же поддерева заходят в scope держателя без ожидания (depth-first).
- `PipelineInfo.task_dependencies`, `parent_task_id`, `completed/failed_tasks` — только bookkeeping: в коде нет ни одного места, где шаг ждёт завершения зависимостей или выбирает порядок по графу. Порядок задаёт вызывающий (LLM-координатор).
- У Anthropic фазы — «по одной, в порядке `phases`, каждая не более одного раза, но API это не гарантирует» [A]. У grid даже такой негарантированной структуры нет — только соглашение в промпте.

### 2.2. Восстановление после падения процесса
**Установлено [G]: resume/replay оркестрации нет; часть наблюдаемости переживает рестарт.**
- Пайплайны — in-memory singleton Dict (`pipeline_registry.py:104-106`); background-раны — in-memory (`core/background_agents.py:86`). При crash пайплайны, статусы ранов и незавершённые background-агенты теряются полностью; финализировать «зависшие» статусы на рестарте некому.
- Персистентно: история диалогов per agent/context (SQLiteSession, `core/agent_factory.py:288`) и дерево трассировки (`ExecutionTracer`, SQLite traces/nodes, `core/tracing/tracer.py:339-347`) — видно, что делали, но продолжить нельзя.
- Контраст внутри grid: `grid_control/service.py:97-110` имеет journal-восстановление (на рестарте `pending("running")` → failed, `pending("queued")` перезапускается) — паттерн существует в смежной подсистеме, но не перенесён на оркестрацию.
- У Anthropic: run живёт на сервере и переживает отключение клиента; клиент после переподключения перестраивает состояние по event-логу с пагинацией и types-фильтром [A]; сервер может перезапустить упавшего агента на новом потоке [A]. Как сервер переживает собственные падения — не раскрыто [?].

### 2.3. init_tools и checkpoints
**Установлено [G]: init_tools — предзапускный сбор контекста, НЕ checkpoints; checkpoint-механизма у grid не найдено.**
- `tools/orchestrator_tools.py:376-410`: `init_tools` — JSON-массив тулов; выполняется в `create_dynamic_agent` (`core/agent_factory.py:576-594` → `_execute_init_tools`), результаты препендятся в instructions ДО старта исполнителя; сбой = logger.warning, агент стартует без контекста (мягкая деградация, не отказ).
- Снапшотов состояния/промежуточных результатов с продолжением (checkpoints в смысле Anthropic event-rebuild или Claude Code resume) в коде grid не найдено (все подсистемы оркестрации прочитаны; «не найдено» при полном чтении соответствующих модулей — здесь правомерно «отсутствует»).
- Beads notes (заметки задач) — best-effort checkpoints для координатора/человека (что проверено, артефакт, остаток), НЕ runtime-resume оркестрации: они не восстанавливают пайплайны/раны и не заменяют машинно-восстановимое состояние.

### 2.4. Сроки в очереди (queue deadlines)
**Установлено [G]: дедлайн background-рана отсчитывается от постановки, а не от получения слота.**
- `core/background_agents.py:144-151`, комментарий в коде: «The deadline starts at launch, not when a queued run acquires a worker slot». При `max_concurrency=4` и >4 задачах хвост очереди сгорает по таймеру, ни разу не начав работу.
- У Anthropic lifetime run — 24h по умолчанию; время ожидания на клиенте и паузы тоже съедают lifetime; run может закончиться `timeout_error` на паузе [A] — та же wall-clock семантика, но с явными статусами (`idle`, `budget_reached`) и паузой/возобновлением, которых у grid нет.

## 5. Приоритизированный план улучшений grid (НЕ реализовывать в этой задаче)

### P0 — надёжность и корректность

**P0-1. Персистентность и восстановление пайплайнов.**
- Точка изменения: `core/tracing/pipeline_registry.py` (journal статусов шагов в SQLite по образцу `grid_control/service.py:97-110`); `core/background_agents.py` — та же journal-таблица для ранов.
- Что делаем: запись при `register_task`/`mark_task_completed`; при старте процесса незавершённые пайплайны помечать orphaned/failed (не «тихо терять»); переигрывание незавершённых шагов — отдельно (P1).
- Критерий: unit-тест «kill -9 в середине пайплайна → рестарт → все пайплайны имеют терминальный статус, ни один не RUNNING».
- Метрика: доля пайплайнов без терминального статуса после рестарта = 0 (сейчас 100% потерь in-memory).

**P0-2. Дедлайн background-ранов от получения слота (или явный выбор семантики).**
- Точка изменения: `core/background_agents.py:144-151` — запуск `asyncio.wait_for` после `async with self._semaphore`, либо отдельный `queue_deadline`/`work_deadline`.
- Критерий: детерминированный тест на fake clock (реальные 60s не ждём) с запасом между work-таймаутом и дедлайном очереди: «5 ранов, work ≈ timeout + запас, max_concurrency=4, дедлайн отсчитывается от получения слота → все completed, ни одного timed_out-в-очереди». Тест «60s при timeout=60s» некорректен: гонка на границе таймера делает результат флейки.
- Метрика: число timed_out ранов, не получивших ни одного модельного вызова = 0.

**P0-3. Явные ошибки вместо тихих ❌-строк для WRITE вне write_paths.**
- Точка изменения: `core/parallel_lanes.py` (`_outside_scope` → структурированная ошибка/исключение с путём и допустимой зоной, ловимая координатором).
- Критерий: тест «координатор получает структурированную ОШИБКУ ПОЛИТИКИ с путём и допустимой зоной». Отказ WRITE вне write_paths — это отказ политики, НЕ автоматически retryable: его нельзя помечать retryable и нельзя переигрывать вслепую (иначе координатор повторит тот же запрещённый путь). Ре-попытка допустима только с изменённым, разрешённым путём по решению координатора.
- Метрика: доля WRITE-отказов, где координатор получил структурированную причину (видно в трассировке) = 100% (было — тихие ❌-строки). Повтор запрещённого пути политикой = 0.

### P1 — масштаб и функциональная полнота

**P1-1. Fan-out для MCP/agent-инструментов.** Точка: `tools/parallel_tools.py::_plan` — допуск read-only MCP-тулов; мутации остаются сериализованными через lane.changes. Критерий: тест параллельного MCP-read при max_parallel>1; мутации по-прежнему сериализованы. Метрика: доля типов тулов, доступных в parallel (цель: все READ/EGRESS).

**P1-2. Конфигурируемые и задокументированные лимиты фан-аута.** Точки: `tools/parallel_tools.py` (MAX_CALLS=16 → конфиг с default 16; max_parallel default 4 — в доку оркестрации), `core/background_agents.py` (max_concurrency — в конфиг), валидация в `core/tool_check.py`. Метрика: benchmark §6 — не менее 2x ускорения wall-time на fan-out задаче при ≤1.3x cost_usd.

**P1-3. Бюджетный стоп/пауза оркестрации (семантика budget_reached).** Точки: `core/model_access.py` (SpendTally — проверка порога перед каждым модельным вызовом в `run_agent_object`), статус пайплайна PAUSED рядом с RUNNING/CANCELLING/EMERGENCY_STOPPED. Критерий: тест «порог достигнут на шаге 3 из 10 → PAUSED, отчёт со spend и завершёнными шагами; поднятие порога → продолжение». Метрика: перерасход сверх бюджета ≤ (число параллельно in-flight вызовов × цена вызова). Строгий overshoot = 0 достижим только при reservation/in-flight-bound (резерв или проверка порога перед каждым вызовом); без этого «перерасход = 0» — недостижимый критерий, и его нельзя ставить как обязательный.

**P1-4. Пиннирование конфигурации исполнителей (по образцу Anthropic versioning).** Точка: `core/agent_factory.py::create_dynamic_agent` — хэш (instructions+tools+model) в трассировку. Метрика: идентификация конфигурации в 100% записей benchmark-прогонов.

### P2 — качество и наблюдаемость

**P2-1. Событийная модель run'а.** Точки: `core/tracing/events.py` + `core/run_stream.py` — события run.created/phase_started/phase_ended/step_started/step_ended/status_ended с результатом (UI-фундамент уже есть: `web_chat/plan_board.py`). Метрика: тест перестроения состояния run из event-лога после переподключения (аналог «rebuild run state» [A]).

**P2-2. Автоматический retry упавших шагов.** Точка: `pipeline_registry.run_serialized_step` (политика transient-only по `core/factory/failures.py::is_retriable`). Ограничение: авто-retry только для ИДЕМПОТЕНТНЫХ шагов/операций и при наличии ключа дедупликации; общий replay WRITE/EXEC запрещён (повтор побочных эффектов). Метрика: доля пайплайнов, завершённых при ≤1 транзиентном сбое идемпотентного шага = 100%.

**P2-3. Рекомендации «когда оркестрировать» в промпте координатора** (аналог «Tell the agent when to use a run» [A]): простые задачи — сам, больше N единиц работы — fan-out. Метрика: снижение доли оркестраций на тривиальных задачах (по трассировке) без потери покрытия.

### P0/P1 — практическая рекомендация: исполняемый typed workflow поверх текущих примитивов

Проектная цель (не реализовано, не измерено): не изобретать новый рантайм, а надстроить над уже существующими примитивами grid (`orchestrate`, `parallel`, `pipeline_registry`) слой **typed workflow/DAG**, где шаги описаны типами и явными зависимостями. Тогда `PipelineRegistry` становится исполнителем (ждёт зависимости, выбирает порядок по графу), а не только трассировщиком; это закрывает главный разрыв из §3.1/§3.4 малой кровью.

- **Typed steps + deps**: каждый шаг — тип (READ/EGRESS/WRITE/EXEC/REVIEW) с объявленными `depends_on`; DAG валидируется до запуска (циклы/висячие deps — отказ на старте).
- **Bounded review loops**: цикл «черновик → ревью» с явным верхним лимитом раундов (аналог repeat-with-limit [A]); исчерпание лимита — терминальный статус с причиной, не бесконечный цикл.
- **Quality gates**: приёмочные контракты (`system_quality`) как отдельные gate-шаги; провал гейта останавливает зависимые ветки и виден в трассировке.
- **Fail-fast для обязательных init_tools**: `init_tools` получают флаг required/optional; сбой required = отказ запуска исполнителя (сейчас — только logger.warning и мягкая деградация без контекста, §2.3).

## 6. Дизайн benchmark «orchestration quality/cost» (локальный, для grid)

1. Корпус: проверяемый репозиторий ~10^5 строк с известным ground truth (синтетический корпус с инжектированными дефектами); два профиля — поиск дефектов (fan-out-heavy) и рефакторинг-миграция (sequence-heavy).
2. Факторы (полная сетка, >=3 повтора на ячейку): режим (single / orchestrate / orchestrate+parallel); max_parallel 4/8/16; глубина фан-аута 8/16; бюджет SpendTally (без лимита / фиксированный, после P1-3).
3. Метрики: качество — precision/recall по дефектам, дубликаты; стоимость — cost_usd (из orchestrate), токены (tally), wall-time и коэффициент совмещения wall_seconds/sum_seconds (из parallel); надёжность — число failed/timed_out шагов, потери от ❌-строк (сравнить намеренные WRITE с выполненными по трассировке); масштабируемость — поведение метрик при 4→8→16.
4. Контроль справедливости: фиксированные model_keys+fallback; пинн конфигурации (P1-4); сиды не контролируются → >=3 прогона и доверительные интервалы; все данные из traces/nodes.
5. Критерии решения: P1-2 принят при >=2x wall-time при <=1.3x cost_usd; P0-2 — timed_out-в-очереди = 0; P1-3 — перерасход в пределах одного request на работающий thread (строгий 0 требует reservation/inflight-bound, см. P1-3).
6. Отчёт: таблица «факторы → метрики» + артефакты прогонов. Тест Anthropic (66 vs 14/15/27 [?]) — только ориентир: их корпус и метод не опубликованы.

## 8. Выводы

1. Anthropic Managed Agents ≠ Claude Code workflows; сравнение — только по Managed Agents API; лимиты 64/1000/24h/10 задокументированы первичкой (оговорка «not guaranteed» — только про 64); runs не вкладываются.
2. Отличия grid (факт; сравнительных метрик нет, превосходство не доказано): контейнерная изоляция и lane-политика, локальный учёт стоимости (model_calls/tokens/cost_usd из каждого orchestrate), локальная трассировка, многоуровневое делегирование.
3. Ограничения grid (факт/проектные пробелы): меньший дефолтный масштаб фан-аута (4↔64; масштаб — настройка), отсутствие resume/восстановления после crash (всё оркестрационное in-memory), отсутствие бюджетного стопа, скрытые константы и тихие ❌-отказы, дедлайны очереди, недоступность MCP-тулов в parallel. Скорость и пропускная способность на реальных задачах не измерялись.
4. PipelineRegistry — не исполнительный DAG (сериализация + трассировка; порядок задаёт LLM). init_tools — предзапускный сбор контекста с мягким сбоем; checkpoints отсутствуют; beads notes — best-effort, не resume.
5. План (проектные цели, не реализовано): P0 (персистентность, дедлайны от слота, явные ошибки политики) → P1 (MCP в parallel, конфигурируемые лимиты, бюджетный стоп, пинн конфигурации) → P2 (event-модель, retry только идемпотентного, промпт-рекомендации) + typed workflow/DAG, bounded review loops, quality gates, fail-fast init_tools + benchmark для измеримой проверки каждого пункта.
